# 추억 장소 아카이브 만들기 4편

<a href="https://python-lesson-red.vercel.app/blogs/memory_place(3)" target="_blank">➡️ 이전 교안 보기</a>

지난 3편에서는 함수형 뷰를 Django 제네릭 뷰로 리팩토링하고,
목록 페이지에 페이지네이션까지 적용했습니다.

이제 프로젝트는 꽤 Django답게 정리된 상태입니다.

* 홈 화면은 `TemplateView`
* 목록 / 상세 / 등록 / 수정 / 삭제는 제네릭 뷰
* 작성자 권한은 믹스인으로 분리
* 목록은 페이지네이션으로 정리

즉, 브라우저에서 사용하는 **웹 서비스 구조**는 어느 정도 안정적으로 잡혔습니다.

하지만 여기서 한 단계 더 나아가려면,
이제는 화면만 보여주는 프로젝트가 아니라 **데이터를 외부에서도 사용할 수 있는 구조**로 확장해야 합니다.

예를 들어 앞으로 아래 같은 상황이 생길 수 있습니다.

* React / Next.js 프론트엔드와 연결하고 싶다.
* 모바일 앱에서 장소 데이터를 불러오고 싶다.
* 지도 화면에서 JSON 데이터만 받아 마커를 뿌리고 싶다.
* 검색 / 필터 / 정렬 기능을 비동기 방식으로 확장하고 싶다.
* 다른 서비스와 데이터를 주고받고 싶다.

이럴 때 필요한 것이 바로 **API** 입니다.

그리고 Django에서 API를 가장 본격적으로 만들 때 사용하는 대표 도구가
**Django REST Framework(DRF)** 입니다.

이번 4편에서는,
기존 추억 장소 아카이브 프로젝트를 DRF로 확장해서
장소 데이터를 **JSON 형태의 API** 로 제공해보겠습니다.

단순히 코드만 붙이는 것이 아니라,
아래 내용을 특히 더 자세하게 이해하는 것을 목표로 하겠습니다.

> **Django의 템플릿 기반 웹 서비스와 DRF 기반 API 서비스는 무엇이 다르고, 왜 DRF가 필요한가?**

즉 이번 편은,
단순 API 실습을 넘어서 **웹과 API의 차이**, **Serializer의 역할**, **DRF 제네릭 뷰의 구조**까지 제대로 이해하는 편입니다.

# 1. API는 도대체 무엇인가?

처음 DRF를 배우거나 익숙하지 않은 분들이 가장 많이 하는 질문은 이것입니다.

> “API가 뭐예요?”

아주 쉽게 말하면,
**API는 화면을 예쁘게 보여주는 것이 아니라 데이터를 주고받기 위한 창구**입니다.

예를 들어 지금까지 우리가 만든 Django 웹 페이지는,
브라우저가 요청을 보내면 서버가 아래처럼 응답합니다.

* HTML 문서
* CSS 적용된 화면
* 버튼, 카드, 템플릿 구조

즉 사람 눈에 보이는 페이지를 주는 구조입니다.

반면 API는 보통 아래처럼 응답합니다.

* JSON 문자열
* 텍스트 기반 데이터
* 다른 프로그램이 읽기 쉬운 형태

즉 API는 **사람이 보기 위한 화면**보다는,
**프론트엔드, 모바일 앱, 다른 서버, 자바스크립트 코드**가 읽기 좋은 형태로 데이터를 전달하는 구조입니다.

예를 들어 장소 목록 API는 이런 느낌으로 응답할 수 있습니다.

```json title="response example"
[
  {
    "id": 1,
    "title": "국립현대미술관 서울",
    "region": "서울 종로구",
    "emotion": "설렘"
  },
  {
    "id": 2,
    "title": "한강공원",
    "region": "서울 영등포구",
    "emotion": "평온"
  }
]
```

이 응답은 예쁜 카드 UI는 없지만,
다른 프로그램이 읽고 활용하기에는 훨씬 좋습니다.

예를 들면 Next.js에서 이 JSON을 받아와서,
원하는 카드 UI를 새로 만들 수 있습니다.

즉,

* Django 템플릿 뷰 = **서버가 화면까지 만들어서 줌**
* DRF API = **서버가 데이터만 주고, 화면은 클라이언트가 자유롭게 구성**

이렇게 이해하면 됩니다.

# 2. 왜 DRF가 필요한가?

그럼 이런 생각이 들 수 있습니다.

> “그냥 Django에서 `JsonResponse` 쓰면 되는 거 아닌가요?”

맞습니다.
아주 단순한 API라면 `JsonResponse` 만으로도 만들 수 있습니다.

하지만 프로젝트가 커지면 아래 문제들이 생깁니다.

* 모델 데이터를 JSON으로 바꾸는 코드가 반복된다.
* 유효성 검사 로직을 직접 하나하나 작성해야 한다.
* 목록 / 상세 / 생성 / 수정 / 삭제 API 패턴이 반복된다.
* 권한 처리, 인증 처리, 페이지네이션, 필터링이 점점 복잡해진다.
* API 문서화, 브라우저 테스트, 확장성이 떨어진다.

DRF는 이런 반복과 복잡함을 줄여주는 프레임워크입니다.

즉 DRF는 단순히 JSON을 주는 도구가 아니라,
**Django에서 API를 체계적으로 만들기 위한 전용 프레임워크**입니다.

DRF를 쓰면 아래가 쉬워집니다.

* 모델 → JSON 변환
* 요청 데이터 검증
* 목록 / 상세 / 생성 / 수정 / 삭제 API 작성
* 권한 / 인증 처리
* 페이지네이션
* 필터 / 검색 기능
* 브라우저에서 테스트 가능한 UI 제공

그래서 Django로 API를 진지하게 만들기 시작하면,
대부분 DRF를 사용합니다.

# 3. JSON은 무엇인가?

API를 이해하려면 JSON도 알아야 합니다.

JSON은 **데이터를 주고받기 위한 아주 흔한 문자열 형식**입니다.

생김새는 파이썬 딕셔너리와 비슷하지만,
엄밀히는 문자열 기반 포맷입니다.

예를 들어 장소 한 개를 JSON으로 표현하면 아래와 비슷합니다.

```json title="json example"
{
  "id": 1,
  "title": "국립현대미술관 서울",
  "address": "서울 종로구 삼청로 30",
  "region": "서울 종로구",
  "emotion": "설렘",
  "latitude": 37.5788,
  "longitude": 126.9804
}
```

JSON은 왜 좋을까요?

* Python도 읽을 수 있다.
* JavaScript도 읽을 수 있다.
* 모바일 앱도 읽을 수 있다.
* 언어와 플랫폼을 거의 가리지 않는다.

즉 JSON은 API 세계에서 사실상 기본 언어 같은 역할을 합니다.

# 4. Serializer는 왜 필요한가?

DRF에서 가장 중요한 개념 중 하나가 **Serializer** 입니다.

처음 보면 이름이 낯설어서 어려워 보이는데,
아주 쉽게 말하면 아래 역할입니다.

> **모델 객체를 JSON으로 바꾸고, 반대로 들어온 데이터를 검증해서 파이썬 객체처럼 다루게 해주는 도구**

즉 Serializer는 두 방향으로 일합니다.

## 4-1. 모델 객체 → JSON

예를 들어 `Place` 모델 객체가 있으면,
Serializer가 그것을 API 응답용 데이터로 바꿔줍니다.

## 4-2. 사용자 입력(JSON) → 검증

나중에 POST / PUT / PATCH 요청이 들어오면,
사용자가 보낸 JSON 데이터가 올바른지 검사하고 저장 준비를 해줍니다.

이 점 때문에 Serializer는 종종 `Form` 과 비슷하게 보입니다.

실제로 비슷한 역할이 있습니다.

* Form / ModelForm: HTML 폼 입력 검증
* Serializer: API 요청 데이터 검증 + 응답 데이터 변환

즉 둘 다 “검증” 역할이 있지만,
**대상 환경이 다릅니다.**

* Form은 템플릿 기반 웹 화면 중심
* Serializer는 API / JSON 중심

이 차이를 꼭 기억해야 합니다.

---

# 5. Django Form / ModelForm 과 Serializer 차이

이 부분은 많이 헷갈리므로 표처럼 정리해보겠습니다.

| 구분      | Form / ModelForm    | Serializer            |
| ------- | ------------------- | --------------------- |
| 주 사용처   | HTML 폼 입력 처리        | API 요청/응답 처리          |
| 데이터 형식  | 브라우저 폼 데이터          | JSON 중심 데이터           |
| 역할      | 입력 검증, 폼 렌더링, 저장 보조 | 입력 검증, JSON 변환, 저장 보조 |
| 주로 쓰는 곳 | Django 템플릿 기반 서비스   | DRF 기반 API 서비스        |

즉 지금 프로젝트에서도 두 개가 공존할 수 있습니다.

* 웹 페이지 등록/수정 화면은 `PlaceForm`
* API 응답/요청은 `PlaceSerializer`

이렇게 역할이 나뉘는 것입니다.

# 7. serializers.py 만들기

이제 `places` 앱 안에 `serializers.py` 파일을 새로 만듭니다.

```python title="places/serializers.py"
from rest_framework import serializers

from .models import Place


class PlaceSerializer(serializers.ModelSerializer):
    author_username = serializers.CharField(source='author.username', read_only=True)

    class Meta:
        model = Place
        fields = [
            'id',
            'title',
            'memory_line',
            'description',
            'address',
            'region',
            'emotion',
            'visited_date',
            'latitude',
            'longitude',
            'image',
            'is_featured',
            'created_at',
            'updated_at',
            'author',
            'author_username',
        ]
        read_only_fields = ['id', 'created_at', 'updated_at', 'author', 'author_username']
```

---

## 7-1. 이 Serializer 코드를 아주 자세히 이해해보기

### `serializers.ModelSerializer`

이 클래스는 `ModelForm` 과 비슷한 느낌입니다.

모델을 기준으로 Serializer를 빠르게 만들 수 있게 도와줍니다.
즉 `Place` 모델 필드를 바탕으로 응답/검증 구조를 자동으로 구성해줍니다.

### `author_username`

```python title="places/serializers.py"
author_username = serializers.CharField(source='author.username', read_only=True)
```

이 필드는 모델에 직접 있는 필드는 아닙니다.
하지만 API 응답에서 작성자 이름도 같이 보여주고 싶어서 추가한 것입니다.

즉 응답 예시는 이런 느낌이 됩니다.

```json title="response example"
{
  "id": 1,
  "title": "국립현대미술관 서울",
  "author": 3,
  "author_username": "baekki"
}
```

`author` 는 사용자 id,
`author_username` 은 사람이 읽기 좋은 이름이라고 보면 됩니다.

### `fields`

API에 노출할 필드를 직접 지정합니다.
즉 모델의 모든 필드를 무조건 다 보여주는 것이 아니라,
어떤 필드를 외부에 공개할지 명확히 결정하는 것입니다.

이 습관은 매우 중요합니다.

### `read_only_fields`

이 필드들은 API 응답에는 나오지만,
클라이언트가 직접 수정 대상으로 보내는 것은 허용하지 않겠다는 뜻입니다.

예를 들어 `author` 는 현재 로그인 사용자로 서버가 정하는 값이어야 하므로,
클라이언트가 임의로 바꾸게 하면 안 됩니다.

# 8. API 뷰 만들기

이제 실제 API 뷰를 만들어보겠습니다.

이번 편에서는 가장 기본이 되는 두 가지부터 만듭니다.

* 장소 목록 API
* 장소 상세 API

`places/views_api.py` 파일을 새로 만들어 아래처럼 작성합니다.

```python title="places/views_api.py"
from rest_framework import generics

from .models import Place
from .serializers import PlaceSerializer


class PlaceListAPIView(generics.ListAPIView):
    queryset = Place.objects.select_related('author').all().order_by('-created_at')
    serializer_class = PlaceSerializer


class PlaceDetailAPIView(generics.RetrieveAPIView):
    queryset = Place.objects.select_related('author').all()
    serializer_class = PlaceSerializer
```

---

## 8-1. 여기서 DRF 제네릭 뷰를 이해해보자

3편에서 Django 제네릭 뷰를 썼듯이,
DRF도 API용 제네릭 뷰를 제공합니다.

이번 편에서는 아래 둘을 사용했습니다.

### `ListAPIView`

여러 개 데이터를 목록 형태로 반환합니다.

즉 `/api/places/` 로 요청하면,
`Place` 여러 개를 JSON 배열로 응답합니다.

### `RetrieveAPIView`

하나의 데이터만 반환합니다.

즉 `/api/places/3/` 으로 요청하면,
`id=3` 인 장소 하나를 JSON 객체로 응답합니다.

이 구조는 Django 제네릭 뷰와 감각이 꽤 비슷합니다.

* Django `ListView` ↔ DRF `ListAPIView`
* Django `DetailView` ↔ DRF `RetrieveAPIView`

차이는 응답 형식입니다.

* `ListView` 는 HTML 템플릿 렌더링
* `ListAPIView` 는 JSON 응답

그래서 이번 편은 3편과 자연스럽게 이어집니다.

# 9. API URL 연결하기

이제 API용 URL을 별도로 연결해야 합니다.

`places/urls.py` 에 API 경로를 같이 넣어도 되지만,
조금 더 깔끔하게 분리하려면 `places/api_urls.py` 파일을 새로 만드는 방식이 좋습니다.

## 9-1. api_urls.py 만들기

```python title="places/api_urls.py"
from django.urls import path

from .views_api import PlaceDetailAPIView, PlaceListAPIView

app_name = 'places_api'

urlpatterns = [
    path('places/', PlaceListAPIView.as_view(), name='place_list_api'),
    path('places/<int:pk>/', PlaceDetailAPIView.as_view(), name='place_detail_api'),
]
```

---

## 9-2. 프로젝트 메인 urls.py 연결하기

프로젝트의 메인 URL 설정 파일에서 API 경로를 연결합니다.

```python title="config/urls.py"
from django.conf import settings
from django.conf.urls.static import static
from django.contrib import admin
from django.urls import include, path
 
urlpatterns = [
    path('admin/', admin.site.urls),
    path('', include('places.urls')),
    path('accounts/', include('django.contrib.auth.urls')),
    path('api/', include('places.api_urls')),
]

if settings.DEBUG:
    urlpatterns += static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)
```

이제 경로 구조는 아래처럼 나뉩니다.

* `/places/` → HTML 목록 페이지
* `/places/1/` → HTML 상세 페이지
* `/api/places/` → JSON 목록 API
* `/api/places/1/` → JSON 상세 API

이 분리가 아주 중요합니다.

웹 화면과 API는 역할이 다르기 때문에,
URL도 분리해두는 것이 훨씬 깔끔합니다.

# 10. DRF Browsable API란 무엇인가?

DRF의 장점 중 하나는 **Browsable API** 입니다.

일반 Django `JsonResponse` 로 API를 만들면,
브라우저에서 그냥 텍스트처럼 JSON이 보일 가능성이 큽니다.

하지만 DRF는 브라우저에서 API를 접속했을 때,
조금 더 보기 쉽게 정리된 화면을 제공합니다.

예를 들어 `http://127.0.0.1:8000/api/places/` 로 들어가면,
브라우저에서 JSON을 보기 쉽게 확인할 수 있고,
나중에는 POST 요청 테스트까지 가능한 화면도 제공됩니다.

왜냐하면 API를 만들고도,
"지금 응답이 잘 오는지" 를 눈으로 바로 확인하기 쉽기 때문입니다.

즉 DRF는 단순히 백엔드 코드만 편하게 하는 것이 아니라,
**학습과 디버깅 경험도 꽤 좋게 만들어줍니다.**

# 13. 왜 4편에서 생성/수정/삭제 API까지 한 번에 안 가는가?

* 데이터를 읽어오는 API

* DRF 제네릭 뷰 감각

이 세 가지에 집중하는 것이 좋습니다.

생성/수정/삭제 API는 다음 단계에서 자연스럽게 확장할 수 있습니다.

# 15. 자주 발생하는 오류와 디버깅 포인트

## 15-1. `ModuleNotFoundError: No module named 'rest_framework'`

DRF 설치가 안 되었거나,
가상환경이 다를 가능성이 큽니다.

확인할 것:

```bash title="terminal"
pip install djangorestframework
```

그리고 현재 가상환경이 맞는지 다시 확인합니다.

---

## 15-2. `rest_framework` 를 `INSTALLED_APPS` 에 안 넣은 경우

설치만 하고 settings 등록을 안 하면,
DRF 화면이 제대로 동작하지 않을 수 있습니다.

```python title="config/settings.py"
INSTALLED_APPS = [
    ...,
    'rest_framework',
]
```

---

## 15-3. `PlaceSerializer` import 오류

파일 위치를 다시 확인하세요.

* `places/serializers.py`
* `places/views_api.py`

그리고 import 경로가 맞는지 확인합니다.

```python title="places/views_api.py"
from .serializers import PlaceSerializer
```

---

## 15-4. 상세 API에서 404가 뜨는 경우

`/api/places/999/` 같이 존재하지 않는 pk를 요청하면 정상적으로 404가 뜹니다.

즉 오류가 아니라,
해당 데이터가 없는 상태일 수 있습니다.

---

## 15-5. 이미지 URL이 이상하게 보이는 경우

개발 환경에서는 `MEDIA_URL` 과 `MEDIA_ROOT`, 그리고 `urls.py` 의 정적 연결 설정을 확인해야 합니다.

```python title="config/urls.py"
if settings.DEBUG:
    urlpatterns += static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)
```

이미지 자체는 문자열 URL로 응답되므로,
JSON에서 `/media/...` 형태로 보이는 것은 정상입니다.

## 16-2. `places/serializers.py`

```python title="places/serializers.py"
from rest_framework import serializers

from .models import Place


class PlaceSerializer(serializers.ModelSerializer):
    author_username = serializers.CharField(source='author.username', read_only=True)

    class Meta:
        model = Place
        fields = [
            'id',
            'title',
            'memory_line',
            'description',
            'address',
            'region',
            'emotion',
            'visited_date',
            'latitude',
            'longitude',
            'image',
            'is_featured',
            'created_at',
            'updated_at',
            'author',
            'author_username',
        ]
        read_only_fields = ['id', 'created_at', 'updated_at', 'author', 'author_username']
```

---

## 16-3. `places/views_api.py`

```python title="places/views_api.py"
from rest_framework import generics

from .models import Place
from .serializers import PlaceSerializer


class PlaceListAPIView(generics.ListAPIView):
    queryset = Place.objects.select_related('author').all().order_by('-created_at')
    serializer_class = PlaceSerializer


class PlaceDetailAPIView(generics.RetrieveAPIView):
    queryset = Place.objects.select_related('author').all()
    serializer_class = PlaceSerializer
```

# 18. 마무리

이번 4편에서는,
기존의 추억 장소 아카이브 프로젝트를 Django REST Framework로 확장해서
**장소 데이터를 API로 제공하는 첫 걸음**을 만들었습니다.

핵심은 아래입니다.

* 웹 화면과 API는 응답 목적이 다르다.
* API는 보통 JSON으로 데이터를 전달한다.
* Serializer는 모델과 JSON 사이를 연결해주는 핵심 도구다.
* DRF는 Django에서 API를 체계적으로 만들기 위한 프레임워크다.
* DRF 제네릭 뷰는 Django 제네릭 뷰와 비슷한 감각으로 사용할 수 있다.

즉 이제부터 이 프로젝트는, 단순히 Django 템플릿으로만 동작하는 서비스가 아니라

**웹 화면 + API를 함께 가진 구조**로 확장되기 시작한 것입니다.

다음 편에서는 이번에 만든 API를 바탕으로,
**검색 / 필터 / 정렬 / 페이지네이션 고도화** 를 붙여서
추억 장소 아카이브를 더 실전적인 프로젝트로 발전시켜보겠습니다.
