# 추억 장소 아카이브 만들기 2-1편

<a href="https://python-lesson-red.vercel.app/blogs/memory_place(1)" target="_blank">이전 교안 보기</a>

지난 1편에서는 **Place 모델 설계**, **관리자페이지 커스터마이징**, **메인/목록 화면 출력**까지 완성했습니다.
이제부터는 이 프로젝트를 단순 조회용 페이지가 아니라, **사용자가 직접 장소를 기록하는 서비스**로 발전시켜야 합니다.

그 첫 단계가 바로 이번 2-1편입니다.

이번 편에서는 아직 지도 검색 자동입력까지 가지 않습니다.
그 전에 반드시 먼저 잡아야 하는 것이 있습니다.

바로 아래 4가지입니다.

* **회원가입 / 로그인 / 로그아웃 기능 붙이기**
* **Place 모델에 작성자(author) 연결하기**
* **함수형 View로 장소 등록 / 수정 / 삭제 만들기**
* **본인 글만 수정/삭제 가능하도록 권한 처리하기**

즉, 이번 2-1편의 핵심은
**“누가 작성했는지 구분되는 추억 장소 CRUD 앱”** 으로 발전시키는 것입니다.

## 왜 지도 검색보다 인증과 CRUD를 먼저 할까요?

처음 보면 많은 분들이 이런 생각을 합니다.

“장소 아카이브니까 지도 검색부터 붙이는 게 더 재밌지 않나요?”

맞습니다. 결과만 놓고 보면 지도 검색이 더 눈에 띕니다.
하지만 학습 흐름으로 보면, 그 전에 먼저 해결해야 할 문제가 있습니다.

예를 들어 사용자가 장소를 검색해서 자동 입력했다고 해도,
그 데이터를 **누가 저장했는지**, **누가 수정할 수 있는지**, **누가 삭제할 수 있는지** 가 정리되어 있지 않으면 서비스 구조가 불안정해집니다.

즉, 장소 검색은 입력 UX의 개선이고,
회원 인증과 CRUD는 **서비스의 기본 뼈대**입니다.

그래서 이번 편에서는 먼저 아래 질문에 답할 수 있도록 만드는 것이 중요합니다.

* 이 장소는 누가 작성했는가?
* 아무나 남의 장소를 수정할 수 있는가?
* 로그인하지 않은 사용자가 글을 작성할 수 있는가?
* 수정 폼과 삭제 흐름은 어떻게 연결되는가?

이 부분이 먼저 안정되어야, 다음 편에서 지도 검색 자동입력을 붙여도 전체 구조가 흔들리지 않습니다.

# 2. Place 모델에 작성자(author) 연결하기

이제 가장 먼저 해야 할 핵심 작업은 **작성자 연결**입니다.

지금 1편의 `Place` 모델은 장소 데이터만 저장합니다.
하지만 이제는 누가 작성했는지까지 기록해야 합니다.
그래야 아래 기능이 가능해집니다.

* 내 글 / 남의 글 구분
* 본인 글만 수정 가능
* 본인 글만 삭제 가능
* 나중에 마이페이지나 내 기록 목록 만들기

## 2-1. models.py 수정하기

```python title="places/models.py"
from django.conf import settings
from django.db import models


class Place(models.Model):
    EMOTION_CHOICES = [
        ('설렘', '설렘'),
        ('그리움', '그리움'),
        ('힐링', '힐링'),
        ('기쁨', '기쁨'),
        ('사색', '사색'),
        ('아련함', '아련함'),
    ]

    author = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE,
        related_name='places',
        verbose_name='작성자',
    )
    title = models.CharField(max_length=100, verbose_name='장소명')
    address = models.CharField(max_length=255, blank=True, verbose_name='주소')
    region = models.CharField(max_length=100, blank=True, verbose_name='지역')
    memory_line = models.CharField(max_length=200, verbose_name='한 줄 추억')
    description = models.TextField(blank=True, verbose_name='상세 설명')
    emotion = models.CharField(
        max_length=20,
        choices=EMOTION_CHOICES,
        default='설렘',
        verbose_name='감정',
    )
    image = models.ImageField(upload_to='places/', blank=True, null=True, verbose_name='대표 이미지')
    visited_date = models.DateField(blank=True, null=True, verbose_name='방문 날짜')
    latitude = models.DecimalField(
        max_digits=10,
        decimal_places=7,
        blank=True,
        null=True,
        verbose_name='위도',
    )
    longitude = models.DecimalField(
        max_digits=10,
        decimal_places=7,
        blank=True,
        null=True,
        verbose_name='경도',
    )
    is_featured = models.BooleanField(default=False, verbose_name='추천 장소 여부')
    created_at = models.DateTimeField(auto_now_add=True, verbose_name='생성일')
    updated_at = models.DateTimeField(auto_now=True, verbose_name='수정일')

    class Meta:
        ordering = ['-created_at']
        verbose_name = '추억 장소'
        verbose_name_plural = '추억 장소들'

    def __str__(self):
        return self.title
```

## 2-2. `settings.AUTH_USER_MODEL` 을 쓰는 이유

여기서 `author` 필드는 `User` 모델과 연결됩니다.
그런데 아래처럼 직접 써도 되지 않을까 싶을 수 있습니다.

```python title="example"
models.ForeignKey(User, ...)
```

하지만 Django에서는 보통 `settings.AUTH_USER_MODEL` 을 사용하는 것이 더 안전합니다.

왜냐하면 나중에 커스텀 유저 모델을 쓰게 되더라도,
이 방식은 그대로 유연하게 대응할 수 있기 때문입니다.

즉, 지금 당장 차이가 커 보이지 않더라도,
**Django에서 유저 모델 참조는 `settings.AUTH_USER_MODEL` 로 쓰는 습관**을 들이는 것이 좋습니다.

그래서 Django/DB에서는 보통 첫 데이터의 id가 0이 아니라 1부터 시작합니다.

# 3. 관리자페이지에서도 작성자 보이도록 수정하기

이제 관리자페이지에서도 작성자를 같이 볼 수 있도록 바꿔보겠습니다.

```python title="places/admin.py"
from django.contrib import admin
from django.utils.html import format_html
from .models import Place


@admin.register(Place)
class PlaceAdmin(admin.ModelAdmin):
    list_display = (
        'id',
        'title',
        'author',
        'region',
        'emotion',
        'is_featured',
        'image_preview',
        'visited_date',
        'created_at',
    )
    search_fields = ('title', 'address', 'region', 'memory_line', 'author__username')
    list_filter = ('emotion', 'region', 'is_featured', 'visited_date', 'author')
    ordering = ('-created_at',)
    readonly_fields = ('created_at', 'updated_at', 'image_preview')
    fields = (
        'author',
        'title',
        'address',
        'region',
        'memory_line',
        'description',
        'emotion',
        'image',
        'image_preview',
        'visited_date',
        'latitude',
        'longitude',
        'is_featured',
        'created_at',
        'updated_at',
    )

    def image_preview(self, obj):
        if obj.image:
            return format_html('<img src="{}" width="100" style="border-radius:8px;" />', obj.image.url)
        return '이미지 없음'

    image_preview.short_description = '썸네일 미리보기'
```

## 3-1. 왜 관리자페이지도 먼저 바꾸는가?

자주 놓치는 부분인데,
웹 화면만 고치고 admin은 그대로 두면 디버깅할 때 불편해집니다.

관리자페이지에서 작성자를 함께 볼 수 있으면,
아래를 아주 빠르게 확인할 수 있습니다.

* 이 장소가 어떤 사용자와 연결되었는가?
* 저장은 정상적으로 되었는가?
* 작성자 연결이 누락되지는 않았는가?

즉, admin은 단순한 백오피스가 아니라
**실습 중 데이터 상태를 확인하는 가장 강력한 디버깅 도구**입니다.

## 4-1. forms.py 만들기

```python title="places/forms.py"
from django import forms
from django.contrib.auth.forms import UserCreationForm
from django.contrib.auth.models import User
from .models import Place


class SignUpForm(UserCreationForm):
    email = forms.EmailField(required=True, label='이메일')

    class Meta:
        model = User
        fields = ('username', 'email', 'password1', 'password2')
        labels = {
            'username': '아이디',
        }


class PlaceForm(forms.ModelForm):
    visited_date = forms.DateInput(attrs={'type': 'date'})

    class Meta:
        model = Place
        fields = [
            'title',
            'address',
            'region',
            'memory_line',
            'description',
            'emotion',
            'image',
            'visited_date',
            'latitude',
            'longitude',
            'is_featured',
        ]
        labels = {
            'title': '장소명',
            'address': '주소',
            'region': '지역',
            'memory_line': '한 줄 추억',
            'description': '상세 설명',
            'emotion': '감정',
            'image': '대표 이미지',
            'visited_date': '방문 날짜',
            'latitude': '위도',
            'longitude': '경도',
            'is_featured': '추천 장소 여부',
        }
        widgets = {
            'title': forms.TextInput(attrs={'placeholder': '예: 서울숲'}),
            'address': forms.TextInput(attrs={'placeholder': '예: 서울 성동구 뚝섬로 273'}),
            'region': forms.TextInput(attrs={'placeholder': '예: 서울'}),
            'memory_line': forms.TextInput(attrs={'placeholder': '예: 처음 같이 산책했던 곳'}),
            'description': forms.Textarea(attrs={'rows': 5, 'placeholder': '그 장소에 대한 자세한 추억을 남겨보세요.'}),
            'latitude': forms.NumberInput(attrs={'step': '0.0000001', 'placeholder': '예: 37.5665000'}),
            'longitude': forms.NumberInput(attrs={'step': '0.0000001', 'placeholder': '예: 126.9780000'}),
        }
```

## 4-2. `PlaceForm` 에서 author를 제외한 이유

여기서 중요한 포인트가 하나 있습니다.

`PlaceForm` 의 `fields` 목록에 `author` 가 없습니다.
이건 실수로 빠진 것이 아니라, **의도적으로 제외한 것**입니다.

왜냐하면 작성자는 사용자가 직접 폼에서 고르는 값이 아니기 때문입니다.
작성자는 현재 로그인한 사용자를 서버 쪽에서 자동으로 넣어야 합니다.

즉,

* 사용자 입력으로 받는 값 → 폼에 포함
* 서버가 자동으로 정해줘야 하는 값 → View에서 처리

이렇게 역할을 나누는 것이 안전합니다.

만약 폼에서 작성자를 직접 받게 만들면,
사용자가 다른 사람 이름으로 데이터를 저장하는 문제도 생길 수 있습니다.

---

## 4-3. `SignUpForm` 을 따로 만드는 이유

회원가입도 그냥 기본 폼을 그대로 써도 되지만,
이번에는 `email` 필드를 추가하고 라벨도 보기 좋게 정리하기 위해 커스텀 폼을 하나 만들었습니다.

실무나 프로젝트에서는 이런 식으로 기본 폼을 살짝 확장해서 쓰는 경우가 많습니다.

## 5-1. config/urls.py 수정하기

```python title="config/urls.py"
from django.urls import include, path

urlpatterns = [

    urlpatterns += static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)
```

## 5-2. `django.contrib.auth.urls` 는 무엇인가요?

이 한 줄이 꽤 중요합니다.

```python title="config/urls.py"
path('accounts/', include('django.contrib.auth.urls'))
```

이 설정을 추가하면 Django가 기본 인증 관련 URL들을 제공합니다.
예를 들면 아래 같은 경로입니다.

* `/accounts/login/`
* `/accounts/logout/`

즉, 로그인/로그아웃 기능의 URL 뼈대를 Django가 이미 제공하는 것입니다.
우리는 여기에 맞는 템플릿만 준비하면 됩니다.

이 방식의 장점은,
인증 시스템의 핵심 로직을 처음부터 직접 다 짜지 않아도 된다는 점입니다.

# 6. 회원가입 / 로그인 / 로그아웃 View 작성하기

이번에는 `places/views.py` 를 확장하겠습니다.

```python title="places/views.py"
from django.contrib import messages
from django.contrib.auth import login
from django.contrib.auth.decorators import login_required
from django.http import Http404
from django.shortcuts import get_object_or_404, redirect, render
from .forms import PlaceForm, SignUpForm
from .models import Place


def home(request):
    featured_places = Place.objects.filter(is_featured=True)[:3]
    latest_places = Place.objects.all()[:6]
    return render(
        request,
        'places/home.html',
        {
            'featured_places': featured_places,
            'latest_places': latest_places,
        },
    )


def place_list(request):
    places = Place.objects.select_related('author').all()
    return render(request, 'places/place_list.html', {'places': places})


def place_detail(request, pk):
    place = get_object_or_404(Place.objects.select_related('author'), pk=pk)
    return render(request, 'places/place_detail.html', {'place': place})


def signup(request):
    if request.user.is_authenticated:
        return redirect('places:home')

    if request.method == 'POST':
        form = SignUpForm(request.POST)
        if form.is_valid():
            user = form.save()
            login(request, user)
            messages.success(request, '회원가입이 완료되었습니다. 바로 로그인되었습니다.')
            return redirect('places:home')
    else:
        form = SignUpForm()

    return render(request, 'registration/signup.html', {'form': form})


@login_required
def place_create(request):
    if request.method == 'POST':
        form = PlaceForm(request.POST, request.FILES)
        if form.is_valid():
            place = form.save(commit=False)
            place.author = request.user
            place.save()
            messages.success(request, '새로운 추억 장소가 등록되었습니다.')
            return redirect('places:place_detail', pk=place.pk)
    else:
        form = PlaceForm()

    return render(
        request,
        'places/place_form.html',
        {
            'form': form,
            'page_title': '장소 기록 추가',
            'submit_label': '장소 저장하기',
        },
    )


@login_required
def place_update(request, pk):
    place = get_object_or_404(Place, pk=pk)

    if place.author != request.user:
        raise Http404('본인 글만 수정할 수 있습니다.')

    if request.method == 'POST':
        form = PlaceForm(request.POST, request.FILES, instance=place)
        if form.is_valid():
            updated_place = form.save(commit=False)
            updated_place.author = request.user
            updated_place.save()
            messages.success(request, '추억 장소가 수정되었습니다.')
            return redirect('places:place_detail', pk=updated_place.pk)
    else:
        form = PlaceForm(instance=place)

    return render(
        request,
        'places/place_form.html',
        {
            'form': form,
            'page_title': '장소 기록 수정',
            'submit_label': '수정 내용 저장하기',
            'place': place,
        },
    )


@login_required
def place_delete(request, pk):
    place = get_object_or_404(Place, pk=pk)

    if place.author != request.user:
        raise Http404('본인 글만 삭제할 수 있습니다.')

    if request.method == 'POST':
        place.delete()
        messages.success(request, '추억 장소가 삭제되었습니다.')
        return redirect('places:place_list')

    return render(request, 'places/place_confirm_delete.html', {'place': place})
```

---

## 6-1. 이번 View에서 꼭 이해해야 하는 핵심 포인트

이번 편의 View는 Django의 핵심 흐름을 많이 담고 있습니다.

### `login_required`

로그인한 사용자만 접근 가능하게 만드는 데코레이터입니다.

이걸 `place_create`, `place_update`, `place_delete` 에 붙였기 때문에,
비회원은 이 기능에 접근할 수 없습니다.

즉, 장소를 쓰는 기능은 공개하지 않고,
읽는 기능만 공개해두는 구조입니다.

---

### `commit=False`

`place_create()` 에서 이 부분이 중요합니다.

```python title="places/views.py"
place = form.save(commit=False)
place.author = request.user
place.save()
```

`commit=False` 는 “아직 DB에 바로 저장하지 말고, Python 객체 상태로 잠깐 들고 있어라” 라는 의미입니다.

왜 이렇게 하냐면,
폼에는 `author` 가 없기 때문입니다.
그래서 먼저 폼 값으로 객체를 만들고,
그 다음 서버에서 `request.user` 를 넣은 뒤 저장하는 것입니다.

이 패턴은 Django에서 정말 자주 나옵니다.

---

### `instance=place`

수정 기능에서는 새 객체를 만드는 것이 아니라,
기존 객체를 수정해야 합니다.
그래서 아래처럼 작성합니다.

```python title="places/views.py"
form = PlaceForm(request.POST, request.FILES, instance=place)
```

이 `instance=place` 가 없으면,
수정처럼 보이지만 실제로는 새 데이터가 하나 더 만들어질 수 있습니다.

즉,

* 생성(Create) → 빈 폼
* 수정(Update) → 기존 객체를 instance로 넣은 폼

이 차이를 꼭 기억해야 합니다.

---

### `place.author != request.user`

이 조건은 권한 처리의 핵심입니다.

```python title="places/views.py"
if place.author != request.user:
    raise Http404('본인 글만 수정할 수 있습니다.')
```

로그인은 했더라도,
남의 글을 수정하거나 삭제하는 것은 막아야 합니다.

이번 실습에서는 가장 단순하게 `Http404` 로 처리했습니다.
이 방식은 “해당 페이지가 없는 것처럼 보이게 하는 처리”입니다.

실무에서는 403 Forbidden 페이지로 분기하는 경우도 많지만,
초반 학습에서는 이 방식이 구현이 더 단순하고 이해하기 쉽습니다.

# 7. URL 연결하기

이제 View와 URL을 연결하겠습니다.

```python title="places/urls.py"
from django.urls import path
from . import views

app_name = 'places'

urlpatterns = [
    path('', views.home, name='home'),
    path('signup/', views.signup, name='signup'),
    path('places/', views.place_list, name='place_list'),
    path('places/create/', views.place_create, name='place_create'),
    path('places/<int:pk>/', views.place_detail, name='place_detail'),
    path('places/<int:pk>/edit/', views.place_update, name='place_update'),
    path('places/<int:pk>/delete/', views.place_delete, name='place_delete'),
]
```

---

## 7-1. URL 설계 포인트

이번 URL은 아주 전형적인 CRUD 구조입니다.

* 목록: `/places/`
* 생성: `/places/create/`
* 상세: `/places/1/`
* 수정: `/places/1/edit/`
* 삭제: `/places/1/delete/`

이런 식으로 패턴을 일정하게 잡아두면,
사용자도 이해하기 쉽고 개발자도 유지보수하기 편합니다.

그리고 이번에는 **회원가입 URL만 직접 만들고**,
로그인/로그아웃은 Django 기본 인증 URL을 활용했습니다.
이렇게 “직접 만들 것”과 “기본 기능을 활용할 것”을 구분하는 것도 좋은 습관입니다.

# 8. 로그인 후 이동 경로 설정하기

로그인/로그아웃 이후 어디로 이동할지도 `settings.py` 에 정해두겠습니다.

```python title="config/settings.py"
LOGIN_REDIRECT_URL = '/'

```

---

## 8-1. 이 설정이 하는 일

### `LOGIN_REDIRECT_URL`

로그인 성공 후 이동할 주소입니다.

로그아웃 후 이동할 주소입니다.

어디로 보낼지 지정하는 주소입니다.

# 9. 템플릿 만들기

이제 화면을 만들어 보겠습니다.
이번 편에서는 기존 UI에 인증/CRUD 흐름이 자연스럽게 녹아들도록 템플릿을 구성하겠습니다.

---

## 9-1. base.html 수정하기

`base.html` 은 이번 프로젝트의 **공통 레이아웃 중심 파일**입니다.

모든 페이지가 이 파일을 상속받기 때문에,
여기에 네비게이션, 메시지 출력, 공통 스타일 연결을 잘 잡아두면
이후 템플릿들이 훨씬 단순해집니다.

특히 이번 편에서 중요하게 볼 부분은 아래입니다.

* 로그인 여부에 따라 메뉴가 달라지는 구조
* 로그아웃을 POST 방식으로 처리하는 부분
* `messages` 를 통해 성공 메시지를 공통 출력하는 부분

즉, 이 파일은 단순한 껍데기가 아니라,
**인증 흐름과 공통 UX를 전체 페이지에 연결하는 핵심 템플릿**이라고 보면 됩니다.

```html title="templates/base.html"
{% load static %}
<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="UTF-8" />
  <meta name="viewport" content="width=device-width, initial-scale=1.0" />
  <title>{% block title %}추억 장소 아카이브{% endblock %}</title>
  <link rel="stylesheet" href="{% static 'css/style.css' %}">
</head>
<body>
  <header class="navbar">
    <div class="container navbar-inner">
      <a href="{% url 'places:home' %}" class="brand">추억 장소 아카이브</a>

      <nav class="nav-links">
        <a href="{% url 'places:home' %}">홈</a>
        <a href="{% url 'places:place_list' %}">전체 장소 보기</a>
        {% if user.is_authenticated %}
          <a href="{% url 'places:place_create' %}">장소 기록 추가</a>
          <form action="{% url 'logout' %}" method="post" class="inline-form">
            {% csrf_token %}
            <button type="submit" class="text-button">로그아웃</button>
          </form>
        {% else %}
          <a href="{% url 'places:signup' %}">회원가입</a>
          <a href="{% url 'login' %}">로그인</a>
        {% endif %}
        <a href="/admin/">관리자페이지</a>
      </nav>
    </div>
  </header>

  {% if messages %}
    <div class="container flash-wrap">
      {% for message in messages %}
        <div class="flash-message">{{ message }}</div>
      {% endfor %}
    </div>
  {% endif %}

  <main>
    {% block content %}{% endblock %}
  </main>

  <footer class="footer">
    <div class="container">
      나만의 장소와 추억을 차곡차곡 기록해두는 작은 아카이브
    </div>
  </footer>
</body>
</html>
```

### base.html에서 중요하게 볼 포인트

#### 1) `user.is_authenticated`

```html title="templates/base.html"
{% if user.is_authenticated %}
```

이 조건문은 현재 사용자가 로그인 상태인지 아닌지를 판별합니다.

이 값을 기준으로,

* 로그인한 사용자는 `장소 기록 추가`, `로그아웃` 메뉴를 보고
* 로그인하지 않은 사용자는 `회원가입`, `로그인` 메뉴를 보게 됩니다.

즉, 하나의 네비게이션 템플릿이 사용자 상태에 따라 다르게 동작하도록 만든 것입니다.

---

#### 2) 로그아웃을 POST 방식으로 처리한 이유

```html title="templates/base.html"
<form action="{% url 'logout' %}" method="post" class="inline-form">
  {% csrf_token %}
  <button type="submit" class="text-button">로그아웃</button>
</form>
```

로그아웃은 단순 링크처럼 보이지만,
실제로는 서버 상태를 바꾸는 동작입니다.
그래서 이번 예제에서는 더 안전하게 **POST 요청 방식**으로 처리했습니다.

이 부분은 초보자가 자주 놓치는 포인트입니다.
로그아웃을 그냥 `<a>` 태그로 처리하려다 405 에러를 만나는 경우도 많기 때문입니다.

---

#### 3) 메시지 프레임워크 출력 위치

```html title="templates/base.html"
{% if messages %}
  <div class="container flash-wrap">
    {% for message in messages %}
      <div class="flash-message">{{ message }}</div>
    {% endfor %}
  </div>
{% endif %}
```

이 구조를 `base.html` 에 넣어두면,
회원가입 성공, 등록 성공, 수정 성공, 삭제 성공 같은 메시지를
모든 페이지에서 공통적으로 보여줄 수 있습니다.

즉, 특정 페이지에만 종속되는 것이 아니라
**프로젝트 전체에서 재사용 가능한 성공 알림 구조**가 되는 것입니다.

---

## 9-2. 회원가입 페이지 만들기

회원가입 화면은 사용자가 이 프로젝트에 처음 진입해

그래서 단순히 입력칸만 배치하기보다,

### signup.html에서 중요하게 볼 포인트

#### 1) `form.non_field_errors`

```html title="templates/registration/signup.html"
{{ form.non_field_errors }}
```

이 코드는 특정 입력칸 하나에만 해당하는 오류가 아니라,
폼 전체 검증 과정에서 발생한 오류를 출력할 때 사용합니다.

예를 들어 비밀번호 검증이나,
폼 전체 조합 검사에서 발생한 메시지가 여기에 나타날 수 있습니다.

즉, 개별 필드 에러만 보여주는 것이 아니라
**폼 전체 에러까지 함께 보여주기 위한 구조**입니다.

---

#### 2) 각 필드를 직접 출력한 이유

```html title="templates/registration/signup.html"
<div class="form-field">
  <label for="id_username">{{ form.username.label }}</label>
  {{ form.username }}
  {{ form.username.errors }}
</div>
```

폼을 그냥 `{{ form.as_p }}` 로 한 번에 출력할 수도 있습니다.
하지만 이번에는 각 필드를 직접 배치했습니다.

그 이유는 아래와 같습니다.

* 레이아웃을 더 예쁘게 제어할 수 있음
* 각 필드 설명과 오류 위치를 명확하게 보여줄 수 있음
* 이후 디자인 수정이나 도움말 추가가 쉬움

즉, 초반에는 조금 길어 보여도,
실제 프로젝트에서는 이렇게 직접 렌더링하는 방식이 훨씬 유연합니다.

## 9-3. 로그인 페이지 만들기

로그인 페이지는 구조상 회원가입 페이지와 비슷하지만,
역할은 조금 다릅니다.

회원가입이 “처음 시작하는 입구”라면,
로그인은 “다시 돌아와서 이어서 기록하는 입구”입니다.

그래서 이번 템플릿도 같은 디자인 톤을 유지하되,
문구는 이어쓰기 경험에 맞게 잡았습니다.

```html title="templates/registration/login.html"
{% extends 'base.html' %}

{% block title %}로그인 | 추억 장소 아카이브{% endblock %}

{% block content %}
<section class="auth-section">
  <div class="container narrow-container">
    <div class="panel-card">
      <div class="panel-head">
        <span class="eyebrow">LOGIN</span>
        <h1>다시 돌아온 당신의 장소 기록</h1>
        <p>로그인하면 내가 남긴 추억 장소를 계속 이어서 관리할 수 있습니다.</p>
      </div>

      <form method="post" class="form-grid">
        {% csrf_token %}
        {{ form.non_field_errors }}

        <div class="form-field">
          <label for="id_username">아이디</label>
          {{ form.username }}
          {{ form.username.errors }}
        </div>

        <div class="form-field">
          <label for="id_password">비밀번호</label>
          {{ form.password }}
          {{ form.password.errors }}
        </div>

        <button type="submit" class="primary-button full-width">로그인</button>
      </form>
    </div>
  </div>
</section>
{% endblock %}
```

### login.html에서 중요하게 볼 포인트

#### 로그인 템플릿 경로가 중요한 이유

이번 로그인 페이지는 우리가 직접 View를 만들지 않았지만,
Django의 기본 인증 시스템이 이 템플릿을 자동으로 찾습니다.

그래서 파일 경로가 아래처럼 정확해야 합니다.

```text title="templates 구조"
templates/
└── registration/
    └── login.html
```

즉, 이름만 맞는다고 되는 것이 아니라
**Django가 기대하는 폴더 경로까지 정확해야 로그인 페이지가 정상 렌더링**됩니다.

## 9-4. 장소 등록 / 수정 폼 페이지 만들기

이번 템플릿은 생성(Create)과 수정(Update)에서 **공통으로 재사용**됩니다.
즉, 장소를 새로 만들 때도 같은 템플릿을 쓰고,
기존 장소를 수정할 때도 같은 템플릿을 씁니다.

이렇게 하면 템플릿 중복을 줄일 수 있고,
버튼 문구나 제목만 바꿔서 같은 UI 구조를 재사용할 수 있습니다.

```html title="templates/places/place_form.html"
{% extends 'base.html' %}

{% block title %}{{ page_title }} | 추억 장소 아카이브{% endblock %}

{% block content %}
<section class="auth-section">
  <div class="container narrow-container">
    <div class="panel-card">
      <div class="panel-head">
        <span class="eyebrow">PLACE FORM</span>
        <h1>{{ page_title }}</h1>
        <p>
          아직은 직접 입력 방식으로 장소를 기록합니다.
          다음 편에서는 여기에 지도 검색 기반 자동입력을 연결할 예정입니다.
        </p>
      </div>

      <form method="post" enctype="multipart/form-data" class="form-grid">
        {% csrf_token %}
        {{ form.non_field_errors }}

        {% for field in form %}
          <div class="form-field">
            <label for="{{ field.id_for_label }}">{{ field.label }}</label>
            {{ field }}
            {% if field.help_text %}
              <small class="help-text">{{ field.help_text }}</small>
            {% endif %}
            {{ field.errors }}
          </div>
        {% endfor %}

        <button type="submit" class="primary-button full-width">{{ submit_label }}</button>
      </form>
    </div>
  </div>
</section>
{% endblock %}
```

### place_form.html에서 중요하게 볼 포인트

#### 1) `enctype="multipart/form-data"`

```html title="templates/places/place_form.html"
<form method="post" enctype="multipart/form-data" class="form-grid">
```

이 속성은 이미지 업로드가 있을 때 반드시 필요합니다.

이번 `PlaceForm` 에는 `image` 필드가 있으므로,
이 설정이 빠지면 텍스트 입력은 들어가도 파일 업로드는 정상 처리되지 않습니다.

초보자가 정말 자주 놓치는 부분이라 꼭 기억해야 합니다.

---

#### 2) `for field in form` 반복문

```html title="templates/places/place_form.html"
{% for field in form %}
```

이 반복문 덕분에 폼 필드를 하나씩 순회하면서,
각 필드의 라벨, 입력창, help_text, 에러를 같은 패턴으로 출력할 수 있습니다.

즉, HTML을 지나치게 길게 늘리지 않으면서도
각 필드별 구조를 일정하게 유지할 수 있는 깔끔한 방식입니다.

---

#### 3) 생성/수정 템플릿을 하나로 합친 이유

이번 템플릿은 `page_title`, `submit_label` 같은 값을 View에서 넘겨받습니다.

그래서 같은 템플릿이더라도,

* 생성 페이지에서는 `장소 기록 추가`
* 수정 페이지에서는 `장소 기록 수정`

처럼 다르게 보이게 할 수 있습니다.

이 방식은 템플릿을 중복해서 두 개 만드는 것보다 훨씬 효율적입니다.

---

## 9-5. 상세 페이지 만들기

상세 페이지는 단순히 장소 정보를 길게 보여주는 화면이 아닙니다.
이번 편에서는 특히 **작성자 확인**, **수정/삭제 권한 연결**, **입력된 데이터 검증** 역할까지 함께 합니다.

즉, 장소 하나의 정보를 가장 완전하게 확인하는 핵심 화면입니다.

```html title="templates/places/place_detail.html"
{% extends 'base.html' %}

{% block title %}{{ place.title }} | 추억 장소 아카이브{% endblock %}

{% block content %}
```

### place_detail.html에서 중요하게 볼 포인트

#### 1) 수정 / 삭제 버튼을 작성자에게만 보여주는 조건문

```html title="templates/places/place_detail.html"
{% if user == place.author %}
  <a href="{% url 'places:place_update' place.pk %}" class="primary-button">수정하기</a>
  <a href="{% url 'places:place_delete' place.pk %}" class="danger-button">삭제하기</a>
{% endif %}
```

이 조건문은 화면 레벨에서 권한을 한 번 더 정리해주는 역할을 합니다.
즉, 본인 글이 아닐 경우에는 수정/삭제 버튼 자체를 숨깁니다.

다만 여기서 꼭 기억해야 할 점이 있습니다.
이것만으로 권한 처리가 끝난 것은 아닙니다.

왜냐하면 사용자는 주소를 직접 입력해서 `/edit/`, `/delete/` 에 접근할 수도 있기 때문입니다.
그래서 View 쪽에서도 별도로 권한 검사를 반드시 해줘야 합니다.

즉,

* 템플릿에서는 버튼을 숨겨 UX를 정리하고
* View에서는 실제 접근을 막아 보안을 처리한다

이 두 단계가 함께 가야 합니다.

---

#### 2) `default` 필터

```html title="templates/places/place_detail.html"
{{ place.address|default:'주소 미입력' }}
```

이런 구조는 값이 비어 있을 때 대체 문구를 보여줍니다.

이번 프로젝트처럼 일부 필드가 선택 입력일 수 있는 경우,
빈칸을 그대로 노출하기보다 이런 식으로 안내 문구를 넣는 편이 훨씬 보기 좋고 사용자 친화적입니다.

그래서 이번에는 바로 삭제하지 않고,
중간에 한 번 더 확인하는 전용 페이지를 만들었습니다.

#### 삭제도 GET이 아니라 POST로 확정하는 이유

그래서 단순 링크 클릭 한 번으로 처리하기보다,
확인 페이지를 거친 뒤 POST 요청으로 마무리하는 구조가 더 안전합니다.

즉, 이번 삭제 페이지는 단순한 안내 화면이 아니라
**실수 방지와 안전한 데이터 처리 흐름을 함께 담당하는 템플릿**입니다.

대신 작성자, 지역, 주소, 방문일처럼 핵심 정보만 카드에 요약합니다.

이렇게 해야 카드 UI가 과하게 무거워지지 않고,
상세 설명은 `상세 보기` 를 눌렀을 때 확인하도록 역할이 분리됩니다.

### home.html에서 중요하게 볼 포인트

#### 1) CTA(Call To Action) 분기

홈 화면 상단에서 로그인 여부에 따라 다른 버튼을 보여주는 구조는 아주 중요합니다.

* 로그인 사용자 → 첫 장소 기록하기

이렇게 해야 사용자에게 지금 가장 필요한 행동을 바로 안내할 수 있습니다.

---

#### 2) 추천 장소 / 최근 장소의 역할 구분

홈에서는 같은 카드 UI를 쓰더라도 섹션 역할이 다릅니다.

* 추천 장소: 프로젝트의 대표적인 장소를 먼저 보여주는 영역
* 최근 등록된 장소: 가장 최근 데이터 흐름을 보여주는 영역

이렇게 섹션의 의미를 나누면,
화면이 더 풍부해지고 단순 목록보다 완성도 있는 서비스처럼 보이게 됩니다.

# 12. 서버 실행 후 테스트하기

이제 서버를 실행합니다.

```bash title="terminal"
python manage.py runserver
```

그리고 아래 순서로 꼭 직접 테스트해보세요.

## 12-1. 회원가입 테스트

* `http://127.0.0.1:8000/signup/` 접속
* 아이디 / 이메일 / 비밀번호 입력
* 회원가입 후 자동 로그인되는지 확인

## 12-2. 로그인 / 로그아웃 테스트

* 로그아웃 버튼 클릭
* 다시 로그인 페이지로 접속
* 로그인 성공 후 홈으로 이동하는지 확인

## 12-3. 장소 생성 테스트

* 로그인 상태에서 `장소 기록 추가` 클릭
* 장소명, 주소, 지역, 한 줄 추억 입력
* 저장 후 상세 페이지로 이동하는지 확인
* 상세 페이지에 작성자(username)가 보이는지 확인

## 12-4. 장소 수정 테스트

* 내가 작성한 글 상세 페이지에서 `수정하기` 클릭
* 내용 변경 후 저장
* 수정 결과가 정상 반영되는지 확인

## 12-5. 장소 삭제 테스트

* 내가 작성한 글 상세 페이지에서 `삭제하기` 클릭
* 삭제 확인 페이지에서 확정
* 목록 페이지로 이동하며 해당 데이터가 사라지는지 확인

## 12-6. 권한 테스트

* 사용자 A로 글 작성
* 로그아웃 후 사용자 B로 로그인
* 사용자 A 글 상세 페이지 접속
* 수정 / 삭제 버튼이 보이지 않는지 확인
* 직접 `/edit/`, `/delete/` 주소를 쳐도 막히는지 확인

## 13-1. `NoReverseMatch at /`

원인:
URL 이름이 잘못되었거나, `place_detail` 같은 경로가 아직 연결되지 않았을 수 있습니다.

확인할 것:

* `places/urls.py` 의 name 값 확인
* 템플릿의 `{% url 'places:...' %}` 오타 확인

---

## 13-2. 로그인 페이지가 안 뜨는 경우

원인:
`config/urls.py` 에 아래 설정이 빠졌을 가능성이 큽니다.

```python title="config/urls.py"
path('accounts/', include('django.contrib.auth.urls'))
```

또는 `templates/registration/login.html` 경로가 잘못되었을 수 있습니다.

Django 기본 인증 뷰는 이 템플릿 경로를 기대합니다.

---

## 13-3. 이미지 업로드가 안 보이는 경우

원인:
개발환경에서 media 설정이 빠졌을 수 있습니다.

확인할 것:

* `MEDIA_URL`, `MEDIA_ROOT`
* `config/urls.py` 의 `static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)`

---

## 13-4. `NOT NULL constraint failed: places_place.author_id`

원인:
`author` 필드는 필수인데,
저장 전에 `place.author = request.user` 를 넣지 않았을 가능성이 큽니다.

즉, 생성 View에서 아래 코드가 빠졌는지 확인해야 합니다.

```python title="places/views.py"
place = form.save(commit=False)
place.author = request.user
place.save()
```

이 오류는 이번 편에서 정말 자주 나옵니다.

---

## 13-5. 수정인데 새 글이 생기는 경우

원인:
Update View에서 `instance=place` 를 안 넣었을 가능성이 큽니다.

```python title="places/views.py"
form = PlaceForm(request.POST, request.FILES, instance=place)
```

수정 폼은 반드시 기존 객체를 기준으로 만들어야 합니다.

---

## 13-6. 로그아웃 링크 클릭 시 405 에러가 나는 경우

이번 예제에서는 로그아웃을 POST 방식 폼으로 처리했습니다.
그래서 `<a>` 링크가 아니라 `<form method="post">` 를 써야 합니다.

즉, 아래 구조가 맞습니다.

```html title="templates/base.html"
<form action="{% url 'logout' %}" method="post" class="inline-form">
  {% csrf_token %}
  <button type="submit" class="text-button">로그아웃</button>
</form>
```

# 14. 이번 편에서 꼭 이해하고 넘어가야 할 것

이번 2-1편은 단순히 기능을 많이 붙인 편이 아닙니다.
사실 Django에서 아주 중요한 개념들이 한 번에 많이 등장합니다.

이번 편의 핵심 이해 포인트는 아래입니다.

* 인증 기능은 Django 기본 기능을 잘 활용하면 훨씬 빠르게 붙일 수 있다.
* 회원가입은 직접 View와 Form을 만들 수 있다.
* 작성자는 폼에서 받는 값이 아니라 서버가 자동으로 넣어야 한다.
* 생성과 수정은 비슷해 보여도 `instance` 유무가 매우 중요하다.
* 버튼을 숨기는 것만으로는 권한 처리가 끝난 것이 아니다.
* 서버에서도 본인 글만 수정 / 삭제 가능하게 막아야 한다.

이 흐름이 이해되면,
다음부터는 블로그, 게시판, 리뷰앱, 기록앱 등 거의 모든 CRUD 프로젝트에 응용할 수 있습니다.

# 15. 체크리스트

아래 항목을 하나씩 직접 체크해보세요.
이번 편은 인증, 권한, CRUD가 한 번에 들어가기 때문에,
단순히 코드만 작성하는 것보다 **실제로 동작을 하나씩 확인하는 과정**이 훨씬 중요합니다.

특히 아래 체크리스트는 “코드를 썼는가?” 보다
“정말 제대로 동작하는가?” 를 검증하는 용도로 보는 것이 좋습니다.

* ✅ `Place` 모델에 `author` 필드를 추가했다.
* ✅ 마이그레이션을 정상적으로 완료했다.
* ✅ 회원가입 페이지가 정상적으로 열린다.
* ✅ 로그인 / 로그아웃이 정상 동작한다.
* ✅ 로그인한 사용자만 장소 등록 페이지에 접근할 수 있다.
* ✅ 새 장소를 저장하면 작성자가 자동으로 현재 로그인 사용자로 저장된다.
* ✅ 상세 페이지에서 작성자 정보가 보인다.
* ✅ 본인 글만 수정 / 삭제 버튼이 보인다.
* ✅ 다른 사용자 글은 수정 / 삭제할 수 없다.
* ✅ 수정 시 새 글이 생기지 않고 기존 글이 업데이트된다.
* ✅ 삭제 확인 페이지를 거쳐 안전하게 삭제된다.

# 16. 마무리

이번 2-1편에서는 드디어 이 프로젝트가
**“보여주기용 목록 페이지”** 에서
**“사용자별로 직접 기록하는 실제 서비스 형태”** 로 한 단계 올라갔습니다.

이제 우리는 아래 구조를 가지게 되었습니다.

* 사용자 계정이 있다.
* 로그인한 사용자가 직접 장소를 기록할 수 있다.
* 각 장소는 작성자와 연결된다.
* 본인 데이터만 수정 / 삭제할 수 있다.

이제 다음 단계로 갈 준비가 되었습니다.

다음 2-2편에서는 이번에 만든 `PlaceForm` 을 바탕으로,
장소명 / 주소 / 지역 / 위도 / 경도를 사용자가 일일이 입력하지 않아도 되도록
**카카오맵 장소 검색 기반 자동입력 UX** 를 붙여보겠습니다.

즉,
이번 편이 **서비스 구조의 뼈대**였다면,
다음 편은 **입력 경험을 훨씬 더 좋아지게 만드는 UX 확장편**이 됩니다.

CRUD 구조가 안정적으로 잡힌 지금 시점에서 지도 검색을 붙이는 것이,
가장 자연스럽고 가장 덜 헷갈리는 순서입니다.
