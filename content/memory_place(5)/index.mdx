# 추억 장소 아카이브 만들기 5편

<a href="https://python-lesson-red.vercel.app/blogs/memory_place(4)" target="_blank">➡️ 이전 교안 보기</a>

지난 4편에서는 Django REST Framework(DRF)를 프로젝트에 붙여서,
추억 장소 데이터를 **JSON 형태로 조회하는 API** 를 만들었습니다.

그때 만든 것은 아래 두 가지였습니다.

* 장소 목록 조회 API
* 장소 상세 조회 API

즉 4편에서는 **GET 요청 기반의 읽기 API** 를 먼저 만든 상태입니다.

하지만 아직 완전한 API 서비스라고 보기는 어렵습니다.

지금 상태에서는 데이터를 읽기만 할 수 있고, API를 통해 직접 아래 작업은 할 수 없기 때문입니다.

* 새 장소 만들기
* 기존 장소 수정하기
* 기존 장소 삭제하기

즉 지금 DRF는 **Read만 있는 상태**입니다.

그래서 이번 5편에서는,
4편에서 만든 읽기 API를 이어서 **쓰기 API(Create / Update / Delete)** 까지 완성해보겠습니다.

그리고 이번 편에서는 단순히 메서드만 추가하는 것이 아니라,
아래 개념을 특히 중요하게 다룹니다.

> **웹에서는 로그인 제한과 작성자 제한을 어떻게 처리했고, API에서는 그것을 어떻게 바꿔서 처리하는가?**

즉 이번 편의 핵심은 아래 두 줄입니다.

* DRF로 생성 / 수정 / 삭제 API 만들기
* 인증과 권한을 붙여서 아무나 수정/삭제하지 못하게 만들기

이번 편까지 끝나면,
추억 장소 아카이브는 단순한 템플릿 웹 프로젝트를 넘어서
**CRUD가 가능한 API 서비스** 구조까지 갖추게 됩니다.

## 이번 편에서 완성할 결과물

이번 글을 끝내면 아래 상태까지 완성됩니다.

* 장소 생성 API를 만든다.

* 장소 삭제 API를 만든다.
* 로그인한 사용자만 생성할 수 있게 만든다.
* 작성자 본인만 수정 / 삭제할 수 있게 만든다.
* API에서 `author` 를 자동 연결한다.
* `PUT` 과 `PATCH` 의 차이를 이해한다.
* DRF에서 인증 / 권한을 어떻게 다루는지 이해한다.
* 다음 편 검색 / 필터 / 정렬 API 확장으로 자연스럽게 이어지게 만든다.

## 헷갈리기 쉬운 포인트 정리

### 0-1. 인증과 권한은 원래 있었는데, 왜 DRF에서 또 설정하나요?

이전까지는 **웹 페이지(view)** 기준으로 로그인 제한과 작성자 제한을 걸어둔 상태였습니다.  
즉 브라우저에서 접근하는 화면에 대해 권한을 막아둔 것입니다.

하지만 DRF를 만들면서 `/api/...` 라는 **새로운 API 엔드포인트**가 추가되었기 때문에,  
API 쪽에도 별도로 인증과 권한을 설정해야 합니다.

정리하면:

- 기존: **웹 페이지 접근 권한 처리**
- DRF: **API 요청 권한 처리**

즉 규칙은 비슷하지만, **보호해야 하는 입구가 다르기 때문에** DRF에서도 다시 설정해야 합니다.

---

### 0-2. CRUD는 전에 이미 만들었는데, 왜 또 작성하나요?

이전까지 만든 CRUD는 **웹 페이지용 CRUD** 입니다.  
즉 사용자가 브라우저 화면에서 등록/수정/삭제를 하는 흐름입니다.

반면 지금 DRF에서 만드는 CRUD는 **API용 CRUD** 입니다.  
즉 HTML 화면이 아니라 JSON 데이터로 생성/수정/삭제를 처리하는 구조입니다.

정리하면:

- 기존 CRUD: **템플릿 기반 웹 CRUD**
- 지금 CRUD: **DRF 기반 API CRUD**

둘 다 같은 `Place` 데이터를 다루지만,  
하나는 **화면용**, 다른 하나는 **데이터 통신용** 이라서 따로 작성하는 것입니다.

# 1. 왜 이번 교안에서는 생성/수정/삭제 API를 만들어야되나?

4편에서는 Read만 만든거에요!

아직 API 쪽에는 **Create / Update / Delete** 가 빠져 있기 때문입니다.

REST API 학습 흐름으로도 자연스러운 순서는 아래와 같습니다.

1. 조회(GET)
2. 생성(POST)
3. 수정(PUT / PATCH)
4. 삭제(DELETE)

즉 5편은 DRF를 한 단계 더 확장하는 **쓰기 API 편** 이 되어야 합니다.

# 2. HTTP 메서드부터 다시 정리하기

DRF로 쓰기 API를 만들기 전에,
HTTP 메서드 의미를 먼저 확실히 잡고 가야 합니다.

## 2-1. GET

데이터를 조회할 때 사용합니다.

* 목록 조회
* 상세 조회

예)

```text title="example"
GET /api/places/
GET /api/places/3/
```

## 2-2. POST

새 데이터를 생성할 때 사용합니다.

예)

```text title="example"
POST /api/places/create/
```

## 2-3. PUT

기존 데이터를 **전체 수정** 할 때 사용합니다.
즉 필드를 거의 다 보내서 새로 덮어쓰는 느낌입니다.

예)

```text title="example"
PUT /api/places/3/edit/
```

## 2-4. PATCH

기존 데이터를 **부분 수정** 할 때 사용합니다.
즉 바꾸고 싶은 필드만 일부 보내는 방식입니다.

예)

```text title="example"
PATCH /api/places/3/edit/
```

## 2-5. DELETE

기존 데이터를 삭제할 때 사용합니다.

예)

```text title="example"
DELETE /api/places/3/delete/
```

---

## 2-6. PUT 과 PATCH 차이 아주 쉽게 이해하기

이 부분은 초보자가 많이 헷갈립니다.

### PUT

“이 객체를 새 값들로 전체 교체한다” 에 가깝습니다.

즉 title만 바꾸고 싶더라도,
다른 필드들을 함께 보내지 않으면 검증에서 불편할 수 있습니다.

### PATCH

“일부 필드만 바꾼다” 에 가깝습니다.

예를 들어 `emotion` 만 바꾸고 싶다면,
그 값만 보내도 됩니다.

실무에서는 부분 수정이 더 자주 쓰이기 때문에,
`PATCH` 는 꼭 익숙해질 필요가 있습니다.

# 3. 웹에서의 권한 처리와 API에서의 권한 처리 차이

3편에서 웹 페이지를 만들 때는 아래처럼 처리했습니다.

* 로그인한 사용자만 등록 / 수정 / 삭제 가능
* 작성자 본인만 수정 / 삭제 가능

그리고 그때는 아래 같은 도구를 사용했습니다.

* `LoginRequiredMixin`
* `UserPassesTestMixin`

하지만 API에서는 화면 템플릿이 아니라 JSON 응답을 주고받습니다.
따라서 권한 처리 방식도 DRF 스타일로 바뀝니다.

DRF에서는 보통 아래 개념을 씁니다.

* **Authentication(인증)**: 누구인지 확인
* **Permission(권한)**: 이 사용자가 이 작업을 해도 되는지 확인

예를 들어 이번 프로젝트에서는 아래 규칙이 필요합니다.

* 로그인한 사용자만 장소 생성 가능
* 로그인한 사용자만 수정 / 삭제 API 요청 가능
* 작성자 본인만 수정 / 삭제 가능

즉 인증과 권한이 모두 필요합니다.

# 4. 이번 편에서 사용할 API 경로 먼저 보기

이번 편에서는 아래처럼 경로를 잡겠습니다.

* 목록 조회: `GET /api/places/`
* 상세 조회: `GET /api/places/<pk>/`
* 생성: `POST /api/places/create/`
* 수정: `PUT /api/places/<pk>/edit/`
* 부분 수정: `PATCH /api/places/<pk>/edit/`
* 삭제: `DELETE /api/places/<pk>/delete/`

이 구조의 장점은 역할이 명확하다는 점입니다.

물론 REST 스타일을 더 엄격하게 적용하면
하나의 상세 경로에서 `GET / PUT / PATCH / DELETE` 를 모두 처리할 수도 있습니다.

하지만 생성 / 수정 / 삭제 경로를 눈에 띄게 나눠두는 것이 이해하기 쉽습니다.

즉 이번 편은 **학습용으로 더 명확한 경로 구조**를 택합니다.

# 5. DRF 권한 클래스 만들기

이제 가장 중요한 부분 중 하나입니다.

작성자 본인만 수정 / 삭제할 수 있게,
커스텀 권한 클래스를 만들어보겠습니다.

`places/permissions.py` 파일을 새로 만듭니다.

```python title="places/permissions.py"
from rest_framework.permissions import BasePermission, SAFE_METHODS


class IsAuthorOrReadOnly(BasePermission):
    def has_object_permission(self, request, view, obj):
        if request.method in SAFE_METHODS:
            return True
        return obj.author == request.user
```

---

## 5-1. 이 권한 클래스는 무슨 뜻인가?

아주 쉽게 말하면 아래 의미입니다.

* `GET`, `HEAD`, `OPTIONS` 같은 안전한 조회 요청은 허용
* 그 외의 수정 / 삭제 요청은 작성자 본인만 허용

여기서 `SAFE_METHODS` 는 DRF가 미리 제공하는 안전한 메서드 묶음입니다.
보통 조회 계열 요청이라고 이해하면 됩니다.

이번 프로젝트에서는 생성(Create)은 객체가 아직 없기 때문에
`has_object_permission()` 보다 뷰 수준의 인증 처리로 막고,
수정 / 삭제는 이미 존재하는 객체를 기준으로 **작성자인지 검사**하면 됩니다.

즉 역할을 나누면 이렇게 됩니다.

* 생성: 로그인 여부 확인
* 수정 / 삭제: 로그인 여부 + 작성자 여부 확인

# 6. Serializer는 그대로 쓰되, author는 서버가 자동으로 넣기

4편에서 만든 `PlaceSerializer` 는 그대로 활용할 수 있습니다.

```python title="places/serializers.py"
from rest_framework import serializers

from .models import Place


class PlaceSerializer(serializers.ModelSerializer):
    author_username = serializers.CharField(source='author.username', read_only=True)

    class Meta:
        model = Place
        fields = [
            'id',
            'title',
            'memory_line',
            'description',
            'address',
            'region',
            'emotion',
            'visited_date',
            'latitude',
            'longitude',
            'image',
            'is_featured',
            'created_at',
            'updated_at',
            'author',
            'author_username',
        ]
        read_only_fields = ['id', 'created_at', 'updated_at', 'author', 'author_username']
```

여기서 중요한 점은,
`author` 를 여전히 `read_only_fields` 로 두는 것입니다.

왜냐하면 작성자 정보는 클라이언트가 직접 정하는 것이 아니라,
서버에서 현재 로그인 사용자로 자동 연결해야 하기 때문입니다.

즉 API 요청 바디에 `author` 를 억지로 넣지 않아도,
서버가 알아서 현재 사용자로 채워주게 만드는 것이 더 안전합니다.

# 7. 생성 / 수정 / 삭제 API 뷰 만들기

이제 실제 API 뷰를 작성하겠습니다.

이번 편에서는 4편의 `views_api.py` 를 아래처럼 확장합니다.

```python title="places/views_api.py"
from rest_framework import generics, permissions

from .models import Place
from .permissions import IsAuthorOrReadOnly
from .serializers import PlaceSerializer


class PlaceListAPIView(generics.ListAPIView):
    queryset = Place.objects.select_related('author').all().order_by('-created_at')
    serializer_class = PlaceSerializer


class PlaceDetailAPIView(generics.RetrieveAPIView):
    queryset = Place.objects.select_related('author').all()
    serializer_class = PlaceSerializer


class PlaceCreateAPIView(generics.CreateAPIView):
    queryset = Place.objects.select_related('author').all()
    serializer_class = PlaceSerializer
    permission_classes = [permissions.IsAuthenticated]

    def perform_create(self, serializer):
        serializer.save(author=self.request.user)


class PlaceUpdateAPIView(generics.RetrieveUpdateAPIView):
    queryset = Place.objects.select_related('author').all()
    serializer_class = PlaceSerializer
    permission_classes = [permissions.IsAuthenticated, IsAuthorOrReadOnly]


class PlaceDeleteAPIView(generics.DestroyAPIView):
    queryset = Place.objects.select_related('author').all()
    serializer_class = PlaceSerializer
    permission_classes = [permissions.IsAuthenticated, IsAuthorOrReadOnly]
```

---

## 7-1. 각 APIView를 쉽게 이해해보기

### `CreateAPIView`

새 데이터를 생성하는 API용 클래스입니다.

즉 `POST /api/places/create/` 요청을 받으면,
들어온 JSON 데이터를 검증한 뒤 새로운 `Place` 를 저장합니다.

### `RetrieveUpdateAPIView`

하나의 객체를 조회하거나 수정할 수 있는 클래스입니다.

즉 같은 URL에서 아래가 가능합니다.

* `GET` : 현재 데이터 보기
* `PUT` : 전체 수정
* `PATCH` : 부분 수정

이번 편에서는 학습용으로 경로 이름을 `edit/` 로 분리했지만,
내부적으로는 `RetrieveUpdateAPIView` 가 처리합니다.

### `DestroyAPIView`

삭제 전용 API입니다.

즉 `DELETE /api/places/<pk>/delete/` 요청을 받으면,
해당 객체를 삭제합니다.

# 8. `perform_create()` 는 왜 필요한가?

이 부분이 매우 중요합니다.

```python title="places/views_api.py"
def perform_create(self, serializer):
    serializer.save(author=self.request.user)
```

4편에서는 Serializer가 주로 “응답을 JSON으로 바꿔주는 도구”처럼 보였다면,
이번 편에서는 “입력 데이터를 검증하고 저장하는 도구” 역할도 본격적으로 하게 됩니다.

그런데 `author` 는 클라이언트가 직접 보내는 값이 아니어야 합니다.
왜냐하면 사용자가 임의로 다른 사람 id를 넣어버릴 수도 있기 때문입니다.

그래서 서버는 현재 로그인한 사용자를 기준으로,
저장 직전에 `author=self.request.user` 를 직접 넣어줍니다.

이 흐름은 3편의 `form_valid()` 와 감각이 비슷합니다.

* Django 제네릭 뷰: `form_valid()`
* DRF 생성 뷰: `perform_create()`

즉 둘 다 “저장 직전에 서버가 값을 보정하는 자리”라고 이해하면 좋습니다.

# 9. URL 연결하기

이제 API URL도 확장해야 합니다.

`places/api_urls.py` 파일을 아래처럼 수정합니다.

```python title="places/api_urls.py"
from django.urls import path

from .views_api import (
    PlaceCreateAPIView,
    PlaceDeleteAPIView,
    PlaceDetailAPIView,
    PlaceListAPIView,
    PlaceUpdateAPIView,
)

app_name = 'places_api'

urlpatterns = [
    path('places/', PlaceListAPIView.as_view(), name='place_list_api'),
    path('places/create/', PlaceCreateAPIView.as_view(), name='place_create_api'),
    path('places/<int:pk>/', PlaceDetailAPIView.as_view(), name='place_detail_api'),
    path('places/<int:pk>/edit/', PlaceUpdateAPIView.as_view(), name='place_update_api'),
    path('places/<int:pk>/delete/', PlaceDeleteAPIView.as_view(), name='place_delete_api'),
]
```

이렇게 하면 역할이 아주 눈에 잘 보입니다.

* 조회 목록

# 10. config/urls.py 는 기존 accounts/ URL을 유지해야 한다

이 부분은 반드시 기억해야 합니다.

이전 편들에서 이미 로그인 / 로그아웃 기능을 위해
`django.contrib.auth.urls` 를 연결해두었기 때문입니다.

따라서 DRF API를 추가한다고 해서,
기존 `accounts/` URL을 삭제하면 안 됩니다.

즉 최종 `config/urls.py` 는 아래처럼 유지되어야 합니다.

```python title="config/urls.py"
from django.conf import settings
from django.conf.urls.static import static
from django.contrib import admin
from django.urls import include, path

urlpatterns = [
    path('admin/', admin.site.urls),
    path('', include('places.urls')),
    path('accounts/', include('django.contrib.auth.urls')),
    path('api/', include('places.api_urls')),
]

if settings.DEBUG:
    urlpatterns += static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)
```

즉 이번 편은 기존 웹 서비스 URL 위에,
추가로 API URL을 얹는 구조입니다.

* 웹 URL 유지
* accounts URL 유지
* API URL 추가

이렇게 이해하면 됩니다.

# 11. 인증된 사용자만 API 생성 가능하게 만들기

생성 API에는 아래 권한을 넣었습니다.

```python title="places/views_api.py"
permission_classes = [permissions.IsAuthenticated]
```

이 뜻은 아주 단순합니다.

* 로그인하지 않은 사용자는 생성 API 사용 불가
* 로그인한 사용자만 생성 가능

즉 `POST /api/places/create/` 요청은 인증된 사용자만 보낼 수 있어야 합니다.

웹 화면에서는 로그인 페이지로 보내는 식이 많았지만,
API에서는 보통 아래처럼 응답이 옵니다.

* 인증 안 됨 → 401 Unauthorized 또는 403 Forbidden

즉 API는 HTML 화면으로 친절하게 이동시키는 것이 아니라,
**상태 코드와 JSON 응답으로 상황을 알려준다**는 차이가 있습니다.

# 12. 작성자 본인만 수정/삭제 가능하게 만들기

수정 / 삭제 API에는 아래처럼 권한을 넣었습니다.

```python title="places/views_api.py"
permission_classes = [permissions.IsAuthenticated, IsAuthorOrReadOnly]
```

이 의미를 풀면 아래와 같습니다.

1. 먼저 로그인한 사용자여야 한다.
2. 그리고 그 객체의 작성자여야 한다.

즉 남의 글은 API로도 수정 / 삭제할 수 없습니다.

이 부분은 웹에서 하던 규칙을 그대로 API로 옮긴 것입니다.

* 웹: 믹스인으로 권한 제한
* API: DRF permission 클래스로 권한 제한

이 차이를 정확히 느끼는 것이 중요합니다.

현재 프로젝트는 Django의 세션 로그인 방식을 사용하고 있으므로,

- 로그인 후 발급된 sessionid

- 함께 검증에 사용되는 csrftoken

즉, 단순히 POST 요청만 보내서는 안 되고,

## 16-6. 권한 테스트

* 수정 API
* 삭제 API

확인할 것:

* 수정 / 삭제가 거부되는지
* 403 Forbidden 같은 응답이 나오는지

왜냐하면 CRUD API에서 가장 중요한 것 중 하나가 **권한 누락 방지** 이기 때문입니다.

# 17. 자주 발생하는 오류와 디버깅 포인트

## 17-1. 로그인 안 했는데 생성이 안 되는 경우

이건 오히려 정상일 가능성이 큽니다.
생성 API는 `IsAuthenticated` 가 걸려 있기 때문입니다.

즉 먼저 로그인 상태를 확인해야 합니다.

---

## 17-2. `author` 를 직접 보내지 않았는데 저장이 안 되는 경우

`perform_create()` 가 제대로 작성되었는지 확인합니다.

```python title="places/views_api.py"
def perform_create(self, serializer):
    serializer.save(author=self.request.user)
```

이 코드가 빠지면 작성자 자동 연결이 안 됩니다.

---

## 17-3. 남의 글도 수정되는 경우

`permission_classes` 설정을 다시 확인합니다.

```python title="places/views_api.py"
permission_classes = [permissions.IsAuthenticated, IsAuthorOrReadOnly]
```

그리고 `permissions.py` 의 권한 클래스가 올바른지 확인합니다.

---

## 17-4. PUT 요청에서 검증 오류가 많이 나는 경우

PUT은 전체 수정 성격이 강하므로,
필수 필드를 충분히 보내지 않으면 오류가 날 수 있습니다.

이럴 때는 PATCH부터 먼저 테스트해보면 이해가 더 쉽습니다.

---

## 17-5. DELETE 요청 후 데이터가 안 없어지는 것처럼 보이는 경우

브라우저 캐시나 목록 화면 새로고침 문제일 수도 있습니다.
실제로 DB에서 삭제되었는지 admin 화면이나 목록 API에서 다시 확인해보세요.

```python title="places/permissions.py"
from rest_framework.permissions import BasePermission, SAFE_METHODS


class IsAuthorOrReadOnly(BasePermission):
    def has_object_permission(self, request, view, obj):
        if request.method in SAFE_METHODS:
            return True
        return obj.author == request.user
```

## 18-3. `places/views_api.py`

```python title="places/views_api.py"
from rest_framework import generics, permissions

from .models import Place
from .permissions import IsAuthorOrReadOnly
from .serializers import PlaceSerializer


class PlaceListAPIView(generics.ListAPIView):
    queryset = Place.objects.select_related('author').all().order_by('-created_at')
    serializer_class = PlaceSerializer


class PlaceDetailAPIView(generics.RetrieveAPIView):
    queryset = Place.objects.select_related('author').all()
    serializer_class = PlaceSerializer


class PlaceCreateAPIView(generics.CreateAPIView):
    queryset = Place.objects.select_related('author').all()
    serializer_class = PlaceSerializer
    permission_classes = [permissions.IsAuthenticated]

    def perform_create(self, serializer):
        serializer.save(author=self.request.user)


class PlaceUpdateAPIView(generics.RetrieveUpdateAPIView):
    queryset = Place.objects.select_related('author').all()
    serializer_class = PlaceSerializer
    permission_classes = [permissions.IsAuthenticated, IsAuthorOrReadOnly]


class PlaceDeleteAPIView(generics.DestroyAPIView):
    queryset = Place.objects.select_related('author').all()
    serializer_class = PlaceSerializer
    permission_classes = [permissions.IsAuthenticated, IsAuthorOrReadOnly]
```

# 20. 마무리

이번 5편에서는,
4편에서 만든 DRF 조회 API를 이어서 **생성 / 수정 / 삭제 API까지 완성** 했습니다.

이번 편에서 꼭 기억해야 할 핵심은 아래입니다.

* GET만 있으면 읽기 API일 뿐, 아직 완전한 CRUD API는 아니다.
* POST / PUT / PATCH / DELETE 가 들어가야 API가 본격적으로 확장된다.
* Serializer는 응답 변환뿐 아니라 요청 검증에도 핵심 역할을 한다.
* `perform_create()` 로 서버가 작성자를 자동 연결할 수 있다.
* 웹에서는 믹스인으로 권한을 처리했고, API에서는 DRF permission 클래스로 권한을 처리한다.

즉 이제 추억 장소 아카이브는,
웹 화면만 있는 프로젝트도 아니고,
조회만 가능한 API 프로젝트도 아닙니다.

이제는 **실제로 데이터를 만들고, 수정하고, 삭제할 수 있는 CRUD API 구조**까지 갖추게 되었습니다.

다음 편에서는 이번에 만든 API를 바탕으로,
**검색 / 필터 / 정렬 / API 페이지네이션** 을 붙여서
추억 장소 데이터를 더 실전적으로 탐색할 수 있는 구조로 확장해보겠습니다.
