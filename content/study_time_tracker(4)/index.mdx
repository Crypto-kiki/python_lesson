# Django 기초 - 공부시간 기록기 만들기(4) : 실습 앱에서 서비스로, 회원가입과 사용자별 공부기록 만들기

이번 4편에서는 1~3편에서 만든 **공부시간 기록기 CRUD + 제너릭 View + DRF API 구조**를 바탕으로,
이제 이 프로젝트를 **진짜 서비스처럼 보이게 만드는 첫 단계**를 진행합니다.

지금까지의 공부시간 기록기는 브라우저에서 기록을 등록하고 수정하고 삭제하는 실습 앱에 가까웠습니다.
그런데 실제 서비스라면 보통 아래 질문이 생깁니다.

* 누가 작성한 기록인가?
* 로그인한 사람의 기록만 따로 보여줄 수 있는가?
* 아무나 남의 글을 수정하거나 삭제할 수 있으면 안 되지 않는가?
* 홈 화면이 단순 목록이 아니라 서비스 첫 화면처럼 보여야 하지 않는가?

이번 편은 바로 그 부분을 해결합니다.

핵심 흐름은 아래와 같습니다.

```
기존 CRUD 실습 앱 완성
→ 회원 기능 추가
→ Study와 User 연결
→ 로그인한 사용자의 기록만 관리
→ 작성자만 수정/삭제 가능
→ 홈 화면과 메뉴를 서비스형으로 개편
```

이번 편이 끝나면, **회원이 로그인해서 자신의 학습 기록을 관리하는 서비스형 프로젝트**로 바뀌게 됩니다.

# 0. 이번 교안의 목표

| 목표                    | 설명                                   |
| --------------------- | ------------------------------------ |
| 인증(Authentication) 이해 | 회원가입, 로그인, 로그아웃이 왜 필요한지 이해           |
| 사용자별 데이터 분리           | Study 데이터가 누구의 것인지 연결하고, 내 기록만 따로 관리 |
| 권한 처리 이해              | 작성자만 수정/삭제 가능하도록 제한                  |
| 서비스형 화면 구성            | 단순 실습 UI가 아니라 실제 서비스처럼 첫 화면과 메뉴 구성   |

즉 이번 편에서 꼭 머릿속에 남겨야 하는 흐름은 아래입니다.

```
기록 데이터만 있는 앱
→ 사용자를 붙인다
→ 데이터 소유자가 생긴다
→ 내 데이터 / 남의 데이터 개념이 생긴다
→ 권한 처리가 필요해진다
→ 서비스형 구조가 된다
```

이 흐름이 이해되면 이후 5편, 6편, 7편에서 붙일
검색 / 필터 / 회고 / 첨부파일 / AI 요약 기능도 훨씬 자연스럽게 연결할 수 있습니다.

## 지금 프로젝트가 갖추고 있어야 할 것

* 제너릭 View 기준 CRUD가 동작한다.

* 목록 페이지에 페이지네이션이 적용되어 있다.
* DRF용 Serializer / ViewSet / Router 구조가 존재한다.
* 브라우저에서 CRUD가 정상 동작한다.

## 현재 `Study` 모델 상태 복습

3편 기준 `Study` 모델은 아래 구조입니다.

```python title="study/models.py"
from django.db import models


class Study(models.Model):
    CATEGORY_CHOICES = [
        ('python', 'Python'),
        ('django', 'Django'),
        ('algorithm', '알고리즘'),
        ('database', 'Database'),
        ('etc', '기타'),
    ]

    title = models.CharField(max_length=200, verbose_name='공부 제목')
    category = models.CharField(max_length=30, choices=CATEGORY_CHOICES, default='django', verbose_name='카테고리')
    study_date = models.DateField(verbose_name='공부 날짜')
    hours = models.PositiveIntegerField(default=0, verbose_name='시간')
    minutes = models.PositiveIntegerField(default=0, verbose_name='분')
    memo = models.TextField(blank=True, verbose_name='메모')
    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)

    class Meta:
        ordering = ['-study_date', '-created_at']
        verbose_name = '공부 기록'
        verbose_name_plural = '공부 기록들'

    def __str__(self):
        return f'{self.title} ({self.study_date})'

    @property
    def total_minutes(self):
        return self.hours * 60 + self.minutes
```

지금 이 모델에는 중요한 정보가 하나 빠져 있습니다.

바로:

> 이 공부기록이 누구 것인가?

실제 서비스에서는 이 정보가 반드시 필요합니다.

# 4. 왜 이제 회원 기능이 필요한가?

구조를 이해하지 못한다면 아래처럼 생각할 수 있습니다.

> 그냥 기록만 저장하면 되는 거 아닌가요?

실습 단계에서는 맞습니다.
그런데 서비스 단계에서는 문제가 생깁니다.

예를 들어 현재 구조에서는 아래 문제가 있습니다.

* 모든 사용자가 같은 기록 목록을 보게 될 수 있습니다.
* 어떤 기록이 누구의 것인지 알 수 없습니다.
* URL만 알면 남의 기록 수정/삭제가 가능할 수 있습니다.
* “내 공부 통계”, “내 최근 기록”, “내 회고” 같은 화면을 만들기 어렵습니다.

즉 서비스로 가려면 반드시 아래 구조가 필요합니다.

```
사용자(User)
↕
공부기록(Study)
```

이제부터는 `Study`가 혼자 존재하는 것이 아니라,
**어떤 사용자가 작성한 Study인지 연결된 상태**로 가야 합니다.

# 5. User와 Study를 어떻게 연결할까?

Django는 기본적으로 인증용 `User` 모델을 제공합니다.
우리는 이 기본 User를 그대로 활용해도 충분합니다.

즉 이번 편에서는 별도의 커스텀 유저 모델까지는 가지 않고,
기본 User를 이용해 아래처럼 연결합니다.

```
User 1명
→ Study 여러 개 작성 가능
```

즉 관계는 아래와 같습니다.

```
User : Study = 1 : N
```

Django 모델에서는 이런 연결을 `ForeignKey`로 표현합니다.

# 6. Study 모델에 author 필드 추가하기

이제 `Study` 모델에 작성자를 나타내는 `author` 필드를 추가합니다.

```python title="study/models.py"
from django.conf import settings
from django.db import models


class Study(models.Model):
    CATEGORY_CHOICES = [
        ('python', 'Python'),
        ('django', 'Django'),
        ('algorithm', '알고리즘'),
        ('database', 'Database'),
        ('etc', '기타'),
    ]

    author = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE,
        related_name='studies',
        verbose_name='작성자',
        null=True,
        blank=True,
    )
    title = models.CharField(max_length=200, verbose_name='공부 제목')
    category = models.CharField(max_length=30, choices=CATEGORY_CHOICES, default='django', verbose_name='카테고리')
    study_date = models.DateField(verbose_name='공부 날짜')
    hours = models.PositiveIntegerField(default=0, verbose_name='시간')
    minutes = models.PositiveIntegerField(default=0, verbose_name='분')
    memo = models.TextField(blank=True, verbose_name='메모')
    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)

    class Meta:
        ordering = ['-study_date', '-created_at']
        verbose_name = '공부 기록'
        verbose_name_plural = '공부 기록들'

    def __str__(self):
        writer = self.author.username if self.author else '작성자 없음'
        return f'{self.title} - {writer}'

    @property
    def total_minutes(self):
        return self.hours * 60 + self.minutes
```

## 코드 설명

### `settings.AUTH_USER_MODEL`

Django의 사용자 모델을 참조하는 안전한 방식입니다.
기본 User를 쓰더라도 앞으로 확장 가능성을 고려하면 이 방식이 좋습니다.

### `on_delete=models.CASCADE`

작성자가 삭제되면 그 사용자의 공부기록도 함께 삭제되도록 합니다.

### `related_name='studies'`

이제 사용자 객체에서 아래처럼 접근할 수 있습니다.

```
user.studies.all()
```

즉 “이 사용자가 작성한 모든 공부기록”을 쉽게 꺼낼 수 있게 됩니다.

### 왜 처음엔 `null=True, blank=True`를 넣는가?

기존 데이터가 이미 DB에 들어 있을 수 있기 때문입니다.
바로 필수값으로 만들면 마이그레이션 시 기존 데이터 때문에 충돌할 수 있습니다.

실습 및 테스트 단계에서는 먼저 안전하게 필드를 추가한 뒤,
이후 생성 로직에서 자동으로 작성자를 넣는 식으로 진행하는 것이 이해하기 쉽습니다.

# 8. 관리자 페이지에 작성자 보이게 정리하기

모델에 author가 추가되었으니 관리자 화면에서도 보이면 좋습니다.

```python title="study/admin.py"
from django.contrib import admin
from .models import Study


@admin.register(Study)
class StudyAdmin(admin.ModelAdmin):
    list_display = ('id', 'title', 'author', 'category', 'study_date', 'hours', 'minutes', 'created_at')
    list_filter = ('category', 'study_date', 'author')
    search_fields = ('title', 'memo', 'author__username')
    ordering = ('-study_date', '-created_at')
```

## 왜 admin도 함께 손보는가?

관리자 페이지는 개발자가 데이터 상태를 확인하는 가장 빠른 도구입니다.
특히 회원 기능을 붙인 뒤에는 아래를 확인하고 싶어집니다.

* 어떤 기록에 작성자가 연결되었는가?
* 작성자 없이 남아 있는 데이터는 없는가?
* 특정 사용자의 기록이 잘 저장되는가?

즉 admin은 단순 부가 기능이 아니라,
**개발 중 현재 상태를 눈으로 확인하는 관리 도구**입니다.

# 11. 로그인/로그아웃 후 이동할 URL 설정하기

인증 기능을 쓸 때는 로그인 성공 후 어디로 갈지,
로그아웃 후 어디로 갈지를 미리 정해두면 편합니다.

```python title="config/settings.py"
LOGIN_REDIRECT_URL = 'study:list'
LOGOUT_REDIRECT_URL = 'study:home'
LOGIN_URL = 'accounts:login'
```

## 각각 의미

* `LOGIN_REDIRECT_URL` : 로그인 성공 후 이동할 페이지
* `LOGOUT_REDIRECT_URL` : 로그아웃 후 이동할 페이지
* `LOGIN_URL` : 로그인 필요 페이지 접근 시 이동할 로그인 URL

이 설정을 해두면 `LoginRequiredMixin`이나 `@login_required` 같은 기능과도 자연스럽게 연결됩니다.

# 12. 회원가입 폼 만들기

Django는 기본 User 모델용 회원가입 폼으로 `UserCreationForm`을 제공합니다.
이번 편에서는 이 폼을 상속해서 조금 더 보기 좋은 형태로 사용하겠습니다.

```python title="accounts/forms.py"
from django import forms
from django.contrib.auth.forms import UserCreationForm
from django.contrib.auth.models import User


class SignUpForm(UserCreationForm):
    email = forms.EmailField(required=True, label='이메일')

    class Meta:
        model = User
        fields = ('username', 'email', 'password1', 'password2')
        labels = {
            'username': '아이디',
        }
```

## 왜 `UserCreationForm`을 쓰는가?

회원가입에는 단순 입력 필드만 있는 것이 아닙니다.

* 비밀번호 2번 입력 확인
* 비밀번호 유효성 검사
* 사용자 생성 처리

같은 기능이 필요합니다.

이걸 처음부터 직접 짜는 것보다,
Django가 이미 제공하는 `UserCreationForm`을 활용하는 것이 훨씬 좋습니다.

# 13. 회원가입 View 만들기

회원가입은 제너릭 View 중 `CreateView`와 아주 잘 어울립니다.
왜냐하면 “폼 보여주기 + 저장하기” 패턴이기 때문입니다.

```python title="accounts/views.py"
from django.contrib.auth.views import LoginView, LogoutView
from django.urls import reverse_lazy
from django.views.generic import CreateView
from .forms import SignUpForm


class SignUpView(CreateView):
    form_class = SignUpForm
    template_name = 'accounts/signup.html'
    success_url = reverse_lazy('accounts:login')

    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        context['page_title'] = '회원가입'
        return context


class CustomLoginView(LoginView):
    template_name = 'accounts/login.html'
    redirect_authenticated_user = True

    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        context['page_title'] = '로그인'
        return context


class CustomLogoutView(LogoutView):
    pass
```

## 코드 설명

### `SignUpView(CreateView)`

회원가입도 결국 새로운 User를 만드는 작업이므로 CreateView와 잘 맞습니다.

### `CustomLoginView(LoginView)`

Django 기본 로그인 기능을 템플릿만 연결해서 사용합니다.

### `redirect_authenticated_user = True`

이미 로그인한 사용자가 로그인 페이지로 들어오면,
굳이 다시 로그인 폼을 보지 않고 적절한 페이지로 보내주는 옵션입니다.

# 16. 홈 화면 View 추가하기

`study` 앱에 홈 화면용 View를 추가합니다.

```python title="study/views_generic.py"
from django.contrib.auth.mixins import LoginRequiredMixin, UserPassesTestMixin
from django.urls import reverse_lazy
from django.views.generic import CreateView, DeleteView, DetailView, ListView, TemplateView, UpdateView
from .forms import StudyForm
from .models import Study


class HomeView(TemplateView):
    template_name = 'study/home.html'


class StudyListGenericView(LoginRequiredMixin, ListView):
    model = Study
    template_name = 'study/study_list.html'
    context_object_name = 'page_obj'
    paginate_by = 5

    def get_queryset(self):
        return Study.objects.filter(author=self.request.user)

    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        studies = Study.objects.filter(author=self.request.user)
        total_count = studies.count()
        total_minutes = sum(study.total_minutes for study in studies)
        context['total_count'] = total_count
        context['total_hours'] = total_minutes // 60
        context['remain_minutes'] = total_minutes % 60
        context['recent_studies'] = studies[:3]
        return context


class StudyDetailGenericView(LoginRequiredMixin, UserPassesTestMixin, DetailView):
    model = Study
    template_name = 'study/study_detail.html'
    context_object_name = 'study'

    def test_func(self):
        return self.get_object().author == self.request.user


class StudyCreateGenericView(LoginRequiredMixin, CreateView):
    model = Study
    form_class = StudyForm
    template_name = 'study/study_form.html'
    success_url = reverse_lazy('study:list')

    def form_valid(self, form):
        form.instance.author = self.request.user
        return super().form_valid(form)

    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        context['page_title'] = '공부 기록 작성'
        return context


class StudyUpdateGenericView(LoginRequiredMixin, UserPassesTestMixin, UpdateView):
    model = Study
    form_class = StudyForm
    template_name = 'study/study_form.html'

    def test_func(self):
        return self.get_object().author == self.request.user

    def get_success_url(self):
        return reverse_lazy('study:detail', kwargs={'pk': self.object.pk})

    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        context['page_title'] = '공부 기록 수정'
        return context


class StudyDeleteGenericView(LoginRequiredMixin, UserPassesTestMixin, DeleteView):
    model = Study
    template_name = 'study/study_confirm_delete.html'
    success_url = reverse_lazy('study:list')
    context_object_name = 'study'

    def test_func(self):
        return self.get_object().author == self.request.user
```

## 이번 코드에서 꼭 이해할 핵심

### `LoginRequiredMixin`

로그인하지 않은 사용자는 접근할 수 없게 합니다.

즉:

* 내 목록 보기
* 상세 보기
* 작성
* 수정
* 삭제

모두 로그인 사용자만 사용할 수 있게 됩니다.

### `UserPassesTestMixin`

추가 권한 검사를 넣을 수 있는 믹스인입니다.
이번 편에서는 “작성자 본인만 접근 가능” 조건을 넣습니다.

### `test_func()`

현재 요청 사용자와 해당 Study의 작성자가 같은지 검사합니다.

```python
return self.get_object().author == self.request.user
```

이 한 줄이 바로 **작성자 권한 처리의 핵심**입니다.

### `get_queryset()`

목록에서는 로그인한 사용자의 데이터만 보여주기 위해 queryset을 제한합니다.

즉 이제 전체 Study가 아니라,

```python
Study.objects.filter(author=self.request.user)
```

만 보여줍니다.

### `form_valid()`

CreateView에서 저장 직전에 작성자를 자동으로 넣습니다.
사용자가 폼에서 author를 직접 입력하면 안 되기 때문입니다.

```python title="study/urls.py"
from django.urls import path

    HomeView,
    StudyCreateGenericView,
    StudyDeleteGenericView,
    StudyDetailGenericView,
    StudyListGenericView,
    StudyUpdateGenericView,
)
```

하지만 서비스가 되면 보통 아래처럼 분리하는 것이 좋습니다.

* 홈: 소개 / 안내 / CTA 버튼
* 목록: 실제 데이터 관리 화면

즉 URL 구조도 서비스의 역할에 맞게 나뉘어야 합니다.

# 28. StudyForm은 그대로 써도 되는가?

대부분은 그대로 써도 됩니다.
다만 중요한 점은 **author 필드를 form에 넣지 않는 것**입니다.

작성자는 사용자가 직접 선택하는 값이 아니라,
로그인한 사용자로 자동 연결되어야 하기 때문입니다.

즉 StudyForm이 아래처럼 구성되어 있다면 괜찮습니다.

```python title="study/forms.py"
from django import forms
from .models import Study
 
 
class StudyForm(forms.ModelForm):
    class Meta:
        model = Study
        fields = ['title', 'category', 'study_date', 'hours', 'minutes', 'memo']
        widgets = {
            'title': forms.TextInput(attrs={
                'placeholder': '예: Django ORM 복습',
            }),
            'category': forms.Select(),
            'study_date': forms.DateInput(attrs={
                'type': 'date',
            }),
            'hours': forms.NumberInput(attrs={
                'min': 0,
                'placeholder': '예: 2',
            }),
            'minutes': forms.NumberInput(attrs={
                'min': 0,
                'max': 59,
                'placeholder': '예: 30',
            }),
            'memo': forms.Textarea(attrs={
                'rows': 6,
                'placeholder': '오늘 공부한 내용, 어려웠던 점, 다시 복습할 포인트를 적어보세요.',
            }),
        }
        labels = {
            'title': '공부 제목',
            'category': '카테고리',
            'study_date': '공부 날짜',
            'hours': '시간',
            'minutes': '분',
            'memo': '메모',
        }
 
    def clean_minutes(self):
        minutes = self.cleaned_data['minutes']
        if minutes >= 60:
            raise forms.ValidationError('분은 0 이상 59 이하로 입력해주세요.')
        return minutes
```

## 왜 author를 빼야 하나?

만약 사용자가 author를 폼으로 선택할 수 있으면,
남의 이름으로 기록을 만드는 이상한 상황이 생길 수 있습니다.

즉 작성자는 폼 입력값이 아니라,
**서버가 현재 로그인 사용자 기준으로 넣어야 하는 값**입니다.

# 29. 로그인하지 않으면 어떻게 되는가?

지금 우리는 `LoginRequiredMixin`을 붙였기 때문에,
로그인하지 않은 상태에서 아래 페이지에 접근하면 로그인 페이지로 이동합니다.

* `/studies/`
* `/studies/create/`
* `/studies/<pk>/`
* `/studies/<pk>/update/`
* `/studies/<pk>/delete/`

이 흐름이 바로 서비스에서 자주 보는 기본 인증 흐름입니다.

```
로그인 필요 페이지 접근
→ 로그인 페이지로 이동
→ 로그인 성공
→ 원래 가려던 페이지 또는 지정 페이지로 이동
```

# 30. 작성자 권한 처리는 왜 View에서 해야 하나?

초보자는 종종 이렇게 생각합니다.

> 템플릿에서 수정/삭제 버튼만 안 보이게 하면 되는 거 아닌가요?

그것만으로는 부족합니다.
왜냐하면 사용자가 URL을 직접 입력할 수도 있기 때문입니다.

예를 들어 템플릿에서 버튼을 숨겼더라도,
누군가 아래 주소를 직접 입력하면 문제가 생깁니다.

```text
/studies/3/update/
/studies/3/delete/
```

그래서 **진짜 권한 검사는 View에서 해야 합니다.**

이번 편에서는 아래 코드가 핵심입니다.

```python
def test_func(self):
    return self.get_object().author == self.request.user
```

이 조건이 통과하지 못하면 수정/삭제/상세 접근 자체가 막히게 됩니다.

# 31. API 쪽은 어떻게 해야 할까?

3편에서 DRF API를 이미 붙였기 때문에,
이제는 API도 사용자 개념에 맞춰 조금 더 다듬을 필요가 있습니다.

이번 4편에서는 브라우저 중심으로 진행하지만,
나중을 위해 최소한 아래 정도는 알고 넘어가면 좋습니다.

* Serializer에서 author를 읽기 전용으로 둘 수 있다.
* ViewSet의 queryset도 사용자 기준으로 제한할 수 있다.
* 생성 시 `perform_create()`에서 `author=self.request.user`를 넣을 수 있다.

# 32. 변경사항 및 주요 코드 최종본

## views_generic.py의 코드를 views.py로 복사 및 붙여넣기, views_cbv 삭제하기

기존 views_generic과 views_cbv는 함수형과 제네릭의 차이를 알아보기 위한 파일이였으므로 더이상 필요 없습니다.

```python title="study/views.py"
from django.contrib.auth.mixins import LoginRequiredMixin, UserPassesTestMixin
from django.urls import reverse_lazy
from django.views.generic import CreateView, DeleteView, DetailView, ListView, TemplateView, UpdateView
from .forms import StudyForm
from .models import Study
 
 
class HomeView(TemplateView):
    template_name = 'study/home.html'
 
 
class StudyListGenericView(LoginRequiredMixin, ListView):
    model = Study
    template_name = 'study/study_list.html'
    context_object_name = 'studies'
    paginate_by = 5
 
    def get_queryset(self):
        return Study.objects.filter(author=self.request.user)
 
    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        studies = Study.objects.filter(author=self.request.user)
        total_count = studies.count()
        total_minutes = sum(study.total_minutes for study in studies)
        context['total_count'] = total_count
        context['total_hours'] = total_minutes // 60
        context['remain_minutes'] = total_minutes % 60
        context['recent_studies'] = studies[:3]
        return context
 
 
class StudyDetailGenericView(LoginRequiredMixin, UserPassesTestMixin, DetailView):
    model = Study
    template_name = 'study/study_detail.html'
    context_object_name = 'study'
 
    def test_func(self):
        return self.get_object().author == self.request.user
 
 
class StudyCreateGenericView(LoginRequiredMixin, CreateView):
    model = Study
    form_class = StudyForm
    template_name = 'study/study_form.html'
    success_url = reverse_lazy('study:list')
 
    def form_valid(self, form):
        form.instance.author = self.request.user
        return super().form_valid(form)
 
    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        context['page_title'] = '공부 기록 작성'
        return context
 
 
class StudyUpdateGenericView(LoginRequiredMixin, UserPassesTestMixin, UpdateView):
    model = Study
    form_class = StudyForm
    template_name = 'study/study_form.html'
 
    def test_func(self):
        return self.get_object().author == self.request.user
 
    def get_success_url(self):
        return reverse_lazy('study:detail', kwargs={'pk': self.object.pk})
 
    def get_context_data(self, **kwargs):

        context['page_title'] = '공부 기록 수정'
```

# 35. 자주 나오는 실수 정리

## 1) `author`를 form에 넣어버림

이러면 사용자가 작성자를 직접 선택하게 되어 구조가 이상해집니다.
반드시 서버에서 자동 연결하세요.

## 2) `LoginRequiredMixin` 순서를 뒤에 둠

믹스인은 보통 왼쪽에 먼저 두는 편이 자연스럽습니다.

예:

```python
class StudyListGenericView(LoginRequiredMixin, ListView):
```

## 3) `UserPassesTestMixin`만 믿고 버튼은 그대로 둠

보안은 View에서 처리하고,
UX는 템플릿에서도 한 번 더 정리하는 것이 좋습니다.

## 4) 홈과 목록 URL 역할이 섞임

서비스형 구조에서는 홈과 데이터 목록의 역할을 구분하는 편이 더 좋습니다.

## 5) 기존 데이터에 author가 비어 있음

기존에 만들어둔 Study 데이터는 author가 없을 수 있습니다.
admin에서 확인하고 필요하면 새로 작성하거나 연결 상태를 점검하세요.

# 35. 이번 편에서 배운 핵심 문법 정리

## 모델 연결

```python
author = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE)
```

## 로그인 필수

```python
class StudyListGenericView(LoginRequiredMixin, ListView):
```

## 작성자 자동 연결

```python
def form_valid(self, form):
    form.instance.author = self.request.user
    return super().form_valid(form)
```

## 작성자 권한 확인

```python
def test_func(self):
    return self.get_object().author == self.request.user
```

## 사용자별 목록 제한

```python
def get_queryset(self):
    return Study.objects.filter(author=self.request.user)
```
