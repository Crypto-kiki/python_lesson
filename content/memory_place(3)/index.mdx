# 추억 장소 아카이브 만들기 3편

<a href="https://python-lesson-red.vercel.app/blogs/memory_place(2-2)" target="_blank">이전 교안 보기</a>

지난 2-2편에서는 **카카오맵 장소 검색**을 붙여서,
장소명 / 주소 / 지역 / 위도 / 경도가 자동으로 입력되는 UX를 완성했습니다.

이제 사용자는 장소를 직접 일일이 입력하지 않아도,
검색 결과를 클릭해서 훨씬 편하게 추억 장소를 기록할 수 있게 되었습니다.

하지만 내부 코드를 보면 아직 한 가지 정리할 시점이 왔습니다.

현재 CRUD는 **함수형 뷰(Function Based View, FBV)** 로 잘 동작하고 있지만,
프로젝트가 점점 커질수록 아래 문제가 생기기 쉽습니다.

* 비슷한 코드가 반복된다.
* GET / POST 분기 코드가 계속 길어진다.
* 작성/수정/삭제 권한 처리 로직이 여러 함수에 흩어진다.
* 목록 기능이 커질수록 페이지 분리, 정렬, 필터 확장이 번거로워진다.

그래서 이번 3편에서는,
기존 기능을 그대로 유지하면서 구조를 한 단계 더 Django답게 정리해보겠습니다.

이번 편의 핵심은 아래 두 가지입니다.

> **함수형 뷰를 Django 제네릭 뷰로 리팩토링하고, 목록 페이지에 페이지네이션을 적용해 아카이브 구조를 더 확장 가능하게 만들기**

즉 이번 편은 새로운 DB 필드를 추가하는 편이 아니라,
이미 잘 동작하는 프로젝트를 **더 깔끔하고 유지보수하기 좋은 구조로 정리하는 리팩토링 편**입니다.

---

## 이번 편에서 완성할 결과물

이번 글을 끝내면 아래 상태까지 완성됩니다.

* `place_list`, `place_detail`, `place_create`, `place_update`, `place_delete` 를 제네릭 뷰로 전환한다.
* 로그인하지 않은 사용자는 등록 / 수정 / 삭제 화면에 접근할 수 없다.
* 작성자가 아닌 사용자는 수정 / 삭제를 할 수 없다.
* 등록 / 수정 시 작성자(author)가 자동으로 연결된다.
* 목록 페이지에 페이지네이션이 적용된다.
* 데이터가 많아져도 한 번에 일정 개수만 깔끔하게 보여줄 수 있다.
* 기존 템플릿 구조와 URL 이름을 최대한 유지하면서 리팩토링한다.

---

## 왜 2-2 다음에 제네릭 뷰와 페이지네이션을 할까요?

이 순서에도 이유가 있습니다.

2-1편과 2-2편까지는,
우선 **기능이 실제로 동작하는 것**에 집중했습니다.

* 회원가입 / 로그인 / 로그아웃
* 작성자 연결
* 함수형 CRUD
* 카카오맵 자동입력 UX

즉, 서비스의 기본 기능은 이미 충분히 살아 있습니다.

이제 다음 단계는 단순히 기능을 더 붙이는 것이 아니라,
**기존 기능을 더 정돈된 구조로 바꾸는 것**입니다.

왜냐하면 앞으로 이 프로젝트는 여기서 끝나지 않기 때문입니다.

다음 편에서는 DRF API까지 붙일 예정이고,
그 이후에는 검색, 필터, 지도 확장 같은 기능도 계속 커질 수 있습니다.

그런데 내부 뷰 구조가 계속 함수형으로 길어지면,
나중에 수정할 때 아래처럼 부담이 커집니다.

* 같은 패턴을 여러 번 반복해야 한다.
* 권한 처리 누락 가능성이 생긴다.
* 목록 로직 확장 시 코드가 지저분해진다.

그래서 지금이 딱 좋습니다.

* 2-1 / 2-2: 기능이 잘 돌아가게 만들기
* 3편: 그 기능을 제네릭 뷰로 깔끔하게 정리하기
* 4편: DRF API 확장하기

# 0. 이번 편 전체 흐름 먼저 보기

## 이번 편 실습 순서

1. 제네릭 뷰가 왜 필요한지 이해하기
2. 현재 함수형 뷰 구조 다시 점검하기
3. 제네릭 뷰에서 자주 쓰는 클래스 이해하기
4. `views.py` 를 제네릭 뷰 기반으로 전체 리팩토링하기
5. 작성자(author) 자동 연결을 `form_valid()` 로 옮기기
6. 작성자 본인만 수정/삭제하도록 권한 체크 넣기
7. 목록 페이지에 페이지네이션 적용하기
8. `place_list.html` 에 페이지 이동 UI 추가하기
9. CSS에 페이지네이션 스타일 추가하기
10. 전체 동작 테스트 및 디버깅 포인트 정리하기

이번 편의 핵심 기술은 아래 3가지입니다.

* Django Generic View
* LoginRequiredMixin / UserPassesTestMixin
* Pagination

즉 이번 편은 단순히 코드를 줄이는 연습이 아니라,
**Django가 기본 제공하는 구조를 활용해 프로젝트를 더 Django답게 만드는 연습**입니다.

---

# 1. 제네릭 뷰를 왜 쓰는가?

Django는 CRUD 패턴이 매우 자주 나온다는 것을 알고 있습니다.
그래서 목록, 상세, 생성, 수정, 삭제 같은 반복 구조를 위해
미리 만들어둔 클래스 기반 뷰(Class Based View, CBV)를 제공합니다.

대표적으로 아래 클래스들을 자주 씁니다.

* `ListView` : 목록 보기
* `DetailView` : 상세 보기
* `CreateView` : 새 데이터 생성
* `UpdateView` : 기존 데이터 수정
* `DeleteView` : 기존 데이터 삭제
* `TemplateView` : 단순 템플릿 렌더링

우리가 지금 만들고 있는 추억 장소 아카이브도 전형적인 CRUD 서비스이므로,
제네릭 뷰와 아주 잘 맞습니다.

함수형 뷰는 처음 흐름을 익힐 때 매우 좋습니다.
하지만 패턴이 보이기 시작하면,
그 다음부터는 제네릭 뷰로 옮겨가야 코드가 훨씬 정리됩니다.

예를 들어 목록 페이지는 본질적으로 아래 구조입니다.

* 어떤 모델을 보여줄지
* 어떤 템플릿을 쓸지
* 어떤 이름으로 템플릿에 데이터를 넘길지

이 정도가 핵심입니다.

그런데 함수형 뷰에서는 매번 `render()` 와 `queryset` 작성 코드를 직접 써야 합니다.
반면 `ListView` 에서는 필요한 속성 몇 개만 지정하면,
Django가 나머지 흐름을 알아서 처리해줍니다.

즉, 이번 편의 목적은 **반복되는 CRUD 패턴을 더 선언적으로 정리하는 것**입니다.

# 2. 현재 함수형 뷰 구조 다시 보기

2-2편까지의 핵심 CRUD 뷰는 대략 아래와 같은 형태였습니다.

```python title="places/views.py"
from django.conf import settings
from django.contrib import messages
from django.contrib.auth import login
from django.contrib.auth.decorators import login_required
from django.http import Http404
from django.shortcuts import get_object_or_404, redirect, render
from .forms import PlaceForm, SignUpForm
from .models import Place


def home(request):
    featured_places = Place.objects.filter(is_featured=True)[:3]
    latest_places = Place.objects.select_related('author').all()[:6]
    return render(
        request,
        'places/home.html',
        {
            'featured_places': featured_places,
            'latest_places': latest_places,
        },
    )


def place_list(request):
    places = Place.objects.select_related('author').all()
    return render(request, 'places/place_list.html', {'places': places})


def place_detail(request, pk):
    place = get_object_or_404(Place.objects.select_related('author'), pk=pk)
    return render(request, 'places/place_detail.html', {'place': place})


@login_required
def place_create(request):
    if request.method == 'POST':
        form = PlaceForm(request.POST, request.FILES)
        if form.is_valid():
            place = form.save(commit=False)
            place.author = request.user
            place.save()
            messages.success(request, '새로운 추억 장소가 등록되었습니다.')
            return redirect('places:place_detail', pk=place.pk)
    else:
        form = PlaceForm()

    return render(
        request,
        'places/place_form.html',
        {
            'form': form,
            'page_title': '장소 기록 추가',
            'submit_label': '장소 저장하기',
            'kakao_javascript_key': settings.KAKAO_JAVASCRIPT_KEY,
        },
    )


@login_required
def place_update(request, pk):
    place = get_object_or_404(Place, pk=pk)

    if place.author != request.user:
        raise Http404('본인 글만 수정할 수 있습니다.')

    if request.method == 'POST':
        form = PlaceForm(request.POST, request.FILES, instance=place)
        if form.is_valid():
            updated_place = form.save(commit=False)
            updated_place.author = request.user
            updated_place.save()
            messages.success(request, '추억 장소가 수정되었습니다.')
            return redirect('places:place_detail', pk=updated_place.pk)
    else:
        form = PlaceForm(instance=place)

    return render(
        request,
        'places/place_form.html',
        {
            'form': form,
            'page_title': '장소 기록 수정',
            'submit_label': '수정 내용 저장하기',
            'place': place,
            'kakao_javascript_key': settings.KAKAO_JAVASCRIPT_KEY,
        },
    )


@login_required
def place_delete(request, pk):
    place = get_object_or_404(Place, pk=pk)

    if place.author != request.user:
        raise Http404('본인 글만 삭제할 수 있습니다.')

    if request.method == 'POST':
        place.delete()
        messages.success(request, '추억 장소가 삭제되었습니다.')
        return redirect('places:place_list')

    return render(request, 'places/place_confirm_delete.html', {'place': place})
```

이 코드는 충분히 잘 작성되어 있습니다.
처음 CRUD 흐름을 배우기에도 아주 좋습니다.

다만 이제는 패턴이 보입니다.

* 같은 모델 `Place` 를 반복해서 조회한다.
* 등록/수정 시 같은 `PlaceForm` 을 반복해서 쓴다.
* `render()` 와 템플릿 이름 지정이 여러 번 반복된다.
* 수정/삭제 권한 검사도 같은 결로 계속 등장한다.

이 반복을 제네릭 뷰로 옮기면,
코드를 줄이는 것 이상으로 구조가 훨씬 선명해집니다.

# 3. 이번 편에서 사용할 제네릭 뷰 구조 이해하기

이번 편에서 사용할 핵심 클래스는 아래와 같습니다.

## 3-1. ListView

목록 페이지용 클래스입니다.

우리가 직접 `places = Place.objects...` 를 만들고 `render()` 하던 흐름을,
Django가 클래스 내부에서 처리해줍니다.

핵심 설정은 보통 아래 정도입니다.

* `model`
* `template_name`
* `context_object_name`
* `paginate_by`
* `ordering` 또는 `get_queryset()`

## 3-2. DetailView

상세 페이지용 클래스입니다.

기존의 `get_object_or_404()` 역할을 내부적으로 수행합니다.
`pk` 값을 받아 해당 객체 하나를 찾아 템플릿에 넘깁니다.

## 3-3. CreateView

생성 폼과 저장을 담당합니다.

기존의 아래 흐름을 내부적으로 처리합니다.

* GET 요청이면 빈 폼 보여주기
* POST 요청이면 폼 검증하기
* 유효하면 저장하기
* 실패하면 다시 폼 보여주기

우리가 추가로 해야 할 일은,
`author = request.user` 처럼 **자동으로 넣고 싶은 값**을 `form_valid()` 에서 처리하는 것입니다.

## 3-4. UpdateView

수정 폼과 저장을 담당합니다.

기존 객체를 불러와 폼에 채워주고,
수정된 내용을 저장하는 흐름을 맡습니다.

## 3-5. DeleteView

삭제 확인 화면과 실제 삭제를 담당합니다.

다만 삭제 후 어디로 보낼지 `success_url` 을 지정해주어야 합니다.

## 3-6. LoginRequiredMixin / UserPassesTestMixin

이 부분이 아주 중요합니다.

* `LoginRequiredMixin` : 로그인 안 한 사용자는 접근 불가
* `UserPassesTestMixin` : 특정 조건을 통과한 사용자만 접근 가능

이번 프로젝트에서는 등록/수정/삭제에 로그인 제한이 필요하고,
수정/삭제는 **작성자 본인만 허용**해야 하므로 둘 다 매우 잘 맞습니다.

# 4. views.py 전체를 제네릭 뷰 기반으로 리팩토링하기

이제 핵심입니다.
기존 `places/views.py` 를 아래 코드로 정리해보겠습니다.

```python title="places/views.py"
from django.conf import settings
from django.contrib import messages
from django.contrib.auth import login
from django.contrib.auth.mixins import LoginRequiredMixin, UserPassesTestMixin
from django.shortcuts import redirect, render
from django.urls import reverse_lazy
from django.views.generic import CreateView, DeleteView, DetailView, ListView, TemplateView, UpdateView
 
from .forms import PlaceForm, SignUpForm
from .models import Place
 
 
class HomeView(TemplateView):
    template_name = 'places/home.html'
 
    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        context['featured_places'] = Place.objects.filter(is_featured=True)[:3]
        context['latest_places'] = Place.objects.select_related('author').all()[:6]
        return context
 
 
class PlaceListView(ListView):
    model = Place
    template_name = 'places/place_list.html'
    context_object_name = 'places'
    paginate_by = 6
    ordering = ['-created_at']
 
    def get_queryset(self):
        return Place.objects.select_related('author').all().order_by('-created_at')
 
 
class PlaceDetailView(DetailView):
    model = Place
    template_name = 'places/place_detail.html'
    context_object_name = 'place'
 
    def get_queryset(self):
        return Place.objects.select_related('author').all()
 
 
class PlaceCreateView(LoginRequiredMixin, CreateView):
    model = Place
    form_class = PlaceForm
    template_name = 'places/place_form.html'
 
    def form_valid(self, form):
        form.instance.author = self.request.user
        messages.success(self.request, '새로운 추억 장소가 등록되었습니다.')
        return super().form_valid(form)
 
    def get_success_url(self):
        return reverse_lazy('places:place_detail', kwargs={'pk': self.object.pk})
 
    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        context['page_title'] = '장소 기록 추가'
        context['submit_label'] = '장소 저장하기'
        context['kakao_javascript_key'] = settings.KAKAO_JAVASCRIPT_KEY
        return context
 
 
class AuthorRequiredMixin(UserPassesTestMixin):
    def test_func(self):
        place = self.get_object()
        return place.author == self.request.user
 
    def handle_no_permission(self):
        messages.error(self.request, '본인 글만 수정하거나 삭제할 수 있습니다.')
        return redirect('places:place_list')
 
 
class PlaceUpdateView(LoginRequiredMixin, AuthorRequiredMixin, UpdateView):
    model = Place
    form_class = PlaceForm
    template_name = 'places/place_form.html'
    context_object_name = 'place'
 
    def form_valid(self, form):
        form.instance.author = self.request.user
        messages.success(self.request, '추억 장소가 수정되었습니다.')
        return super().form_valid(form)
 
    def get_success_url(self):
        return reverse_lazy('places:place_detail', kwargs={'pk': self.object.pk})
 
    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        context['page_title'] = '장소 기록 수정'
        context['submit_label'] = '수정 내용 저장하기'
        context['kakao_javascript_key'] = settings.KAKAO_JAVASCRIPT_KEY
        return context
 
 
class PlaceDeleteView(LoginRequiredMixin, AuthorRequiredMixin, DeleteView):
    model = Place
    template_name = 'places/place_confirm_delete.html'
    context_object_name = 'place'
    success_url = reverse_lazy('places:place_list')
 
    def delete(self, request, *args, **kwargs):
        messages.success(self.request, '추억 장소가 삭제되었습니다.')
        return super().delete(request, *args, **kwargs)
 
 
 
def signup(request):
    if request.user.is_authenticated:
        return redirect('places:home')
 
    if request.method == 'POST':
        form = SignUpForm(request.POST)
        if form.is_valid():
            user = form.save()
            login(request, user)
            messages.success(request, '회원가입이 완료되었습니다. 바로 로그인되었습니다.')
            return redirect('places:home')
    else:
        form = SignUpForm()
 
    return render(request, 'registration/signup.html', {'form': form})
```

# 5. 각 제네릭 뷰를 아주 쉽게 이해해보기

## 5-1. HomeView

홈 화면은 CRUD가 아니라 단순 템플릿 렌더링 + 일부 데이터 전달입니다.
그래서 `TemplateView` 를 사용했습니다.

```python title="places/views.py"
class HomeView(TemplateView):
    template_name = 'places/home.html'

    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        context['featured_places'] = Place.objects.filter(is_featured=True)[:3]
        context['latest_places'] = Place.objects.select_related('author').all()[:6]
        return context
```

여기서 핵심은 `get_context_data()` 입니다.

기존 함수형 뷰에서는 딕셔너리를 직접 만들어 `render()` 로 넘겼습니다.
제네릭 뷰에서는 이 메서드를 오버라이드해서,
템플릿에 전달할 추가 데이터를 `context` 에 넣어주면 됩니다.

## 5-2. PlaceListView

```python title="places/views.py"
class PlaceListView(ListView):
    model = Place
    template_name = 'places/place_list.html'
    context_object_name = 'places'
    paginate_by = 6

    def get_queryset(self):
        return Place.objects.select_related('author').all().order_by('-created_at')
```

여기서 가장 중요한 줄은 2개입니다.

* `context_object_name = 'places'`
* `paginate_by = 6`

템플릿에서 기존처럼 `places` 라는 이름을 그대로 쓸 수 있게 맞춰준 것이고,
한 페이지에 6개씩 보여주겠다는 뜻입니다.

또한 `get_queryset()` 을 사용해서
작성자 정보까지 미리 함께 불러오도록 `select_related('author')` 를 유지했습니다.

즉 단순 리팩토링이 아니라,
기존 최적화 방향도 그대로 유지하고 있는 것입니다.

## 5-3. PlaceDetailView

```python title="places/views.py"
class PlaceDetailView(DetailView):
    model = Place
    template_name = 'places/place_detail.html'
    context_object_name = 'place'

    def get_queryset(self):
        return Place.objects.select_related('author').all()
```

기존 템플릿은 `place` 라는 이름으로 객체를 받고 있었으므로,
`context_object_name = 'place'` 를 명시해줍니다.

이렇게 해야 템플릿을 최소 수정으로 그대로 재사용할 수 있습니다.

## 5-4. PlaceCreateView

```python title="places/views.py"
class PlaceCreateView(LoginRequiredMixin, CreateView):
    model = Place
    form_class = PlaceForm
    template_name = 'places/place_form.html'

    def form_valid(self, form):
        form.instance.author = self.request.user
        messages.success(self.request, '새로운 추억 장소가 등록되었습니다.')
        return super().form_valid(form)
```

이 부분이 매우 중요합니다.

`CreateView` 는 폼 저장을 내부적으로 처리합니다.
하지만 `author` 는 사용자가 직접 입력하는 필드가 아니라,
로그인한 사용자로 자동 연결해야 합니다.

그래서 저장 직전에 `form.instance.author = self.request.user` 를 넣어주는 것입니다.

즉,
기존 함수형 뷰의 `form.save(commit=False)` 역할을
제네릭 뷰에서는 `form_valid()` 안에서 처리한다고 이해하면 됩니다.

## 5-5. PlaceUpdateView

수정도 거의 같은 원리입니다.

```python title="places/views.py"
class PlaceUpdateView(LoginRequiredMixin, AuthorRequiredMixin, UpdateView):
    model = Place
    form_class = PlaceForm
    template_name = 'places/place_form.html'
    context_object_name = 'place'
```

이미 존재하는 객체를 수정할 때도,
작성자(author)는 그대로 현재 사용자와 연결 상태를 유지해야 하므로
`form_valid()` 에서 다시 지정해주는 방식으로 안정성을 챙겼습니다.

## 5-6. PlaceDeleteView

```python title="places/views.py"

    model = Place
    template_name = 'places/place_confirm_delete.html'
```

삭제는 저장할 폼이 없으므로,
삭제 성공 후 어디로 이동할지만 `success_url` 로 지정하면 됩니다.

# 6. 작성자 본인만 수정/삭제 가능하게 믹스인으로 정리하기

기존 함수형 뷰에서는 아래처럼 매번 직접 검사했습니다.

```python title="places/views.py"
if place.author != request.user:
    raise Http404('본인 글만 수정할 수 있습니다.')
```

이 방식도 틀린 것은 아닙니다.
하지만 수정/삭제처럼 비슷한 권한 조건이 여러 곳에서 반복되면,
이제는 공통 믹스인으로 뽑는 것이 좋습니다.

```python title="places/views.py"
class AuthorRequiredMixin(UserPassesTestMixin):
    def test_func(self):
        place = self.get_object()
        return place.author == self.request.user

    def handle_no_permission(self):
        messages.error(self.request, '본인 글만 수정하거나 삭제할 수 있습니다.')
        return redirect('places:place_list')
```

이 구조의 장점은 아주 큽니다.

* 작성자 검사 로직을 한 곳에 모을 수 있다.
* 수정 뷰와 삭제 뷰에서 같은 권한 규칙을 재사용할 수 있다.
* 나중에 “비공개 글은 관리자만 가능” 같은 정책이 추가되어도 확장하기 쉽다.

이런 식으로 **권한 규칙을 재사용 가능한 단위로 빼는 감각**은 매우 중요합니다.

# 7. URL도 클래스 기반 뷰로 연결하기

뷰를 클래스 기반으로 바꿨다면,
URL도 `.as_view()` 로 연결해야 합니다.

기존 `places/urls.py` 를 아래처럼 정리합니다.

```python title="places/urls.py"
from django.urls import path

from .views import (
    HomeView,
    PlaceCreateView,
    PlaceDeleteView,
    PlaceDetailView,
    PlaceListView,
    PlaceUpdateView,
    signup,
)

app_name = 'places'

urlpatterns = [
    path('', HomeView.as_view(), name='home'),
    path('signup/', signup, name='signup'),
    path('places/', PlaceListView.as_view(), name='place_list'),
    path('places/create/', PlaceCreateView.as_view(), name='place_create'),
    path('places/<int:pk>/', PlaceDetailView.as_view(), name='place_detail'),
    path('places/<int:pk>/edit/', PlaceUpdateView.as_view(), name='place_update'),
    path('places/<int:pk>/delete/', PlaceDeleteView.as_view(), name='place_delete'),
]
```

여기서 중요한 점은,
**URL 이름(name)을 기존과 동일하게 유지한 것**입니다.

이렇게 해야 템플릿의 `{% url 'places:place_detail' place.pk %}` 같은 코드들을 거의 수정하지 않아도 됩니다.

즉 리팩토링할 때는 내부 구조는 바꾸더라도,
외부 인터페이스(URL name)는 최대한 유지하는 습관이 좋습니다.

# 8. 페이지네이션이 실제로 어떻게 동작하는가?

이제 이번 편의 두 번째 핵심입니다.

아카이브 서비스는 시간이 지날수록 데이터가 계속 쌓입니다.
처음에는 장소가 3개, 5개밖에 없어서 한 페이지에 다 보여도 괜찮습니다.

하지만 나중에는 아래 문제가 생깁니다.

* 목록 페이지가 너무 길어진다.
* 첫 화면 로딩이 무거워질 수 있다.
* 사용자가 원하는 글을 찾기 어려워진다.
* UI가 지저분해진다.

그래서 목록은 일정 개수씩 끊어서 보여주는 것이 좋습니다.
이것이 바로 페이지네이션입니다.

이번 편에서는 `paginate_by = 6` 으로 설정했으므로,
한 페이지에 6개의 장소 카드만 보이게 됩니다.

예를 들어 데이터가 총 14개라면 아래처럼 나뉩니다.

* 1페이지: 1~6번째
* 2페이지: 7~12번째
* 3페이지: 13~14번째

그리고 Django는 템플릿 안에서 자동으로 아래 값들을 제공합니다.

* `is_paginated`
* `page_obj`
* `paginator`
* `object_list`

이 값들을 이용하면 페이지 번호 이동 UI를 만들 수 있습니다.

## 9-1. 이 템플릿에서 꼭 이해해야 할 핵심

### `is_paginated`

페이지네이션이 실제로 필요한 상황일 때만 `True` 가 됩니다.
즉 데이터가 적어서 한 페이지로 충분하면,
페이지 이동 버튼 영역은 굳이 보이지 않습니다.

### `page_obj`

현재 페이지 정보를 담고 있는 객체입니다.
예를 들어 아래 같은 값을 확인할 수 있습니다.

* 이전 페이지가 있는지
* 다음 페이지가 있는지
* 현재 몇 페이지인지

### `paginator.page_range`

전체 페이지 번호 범위를 의미합니다.
예를 들어 전체가 5페이지면,
`1, 2, 3, 4, 5` 를 순회할 수 있게 됩니다.

### 현재 페이지 주변 번호만 보여주는 조건

```html title="templates/places/place_list.html"
{% elif num >= page_obj.number|add:'-2' and num <= page_obj.number|add:'2' %}
```

이 조건은 현재 페이지 기준 앞뒤 2개 정도만 보이게 해서,
페이지 번호가 너무 길게 늘어지는 것을 막아줍니다.

예를 들어 현재가 7페이지라면,
5, 6, 7, 8, 9 정도만 보여주는 방식입니다.

이런 작은 UX 디테일이 실제 완성도를 꽤 높여줍니다.

# 13. 자주 발생하는 오류와 디버깅 포인트

## 13-1. `NameError: name 'render' is not defined`

리팩토링하면서 `signup()` 은 함수형으로 남겨두었는데,
`render` import 를 빠뜨리면 발생합니다.

해결:

```python title="places/views.py"
from django.shortcuts import redirect, render
```

## 13-2. `NoReverseMatch` 오류

`success_url` 또는 `get_success_url()` 에서 URL 이름이 다르면 발생합니다.

확인할 것:

* `places:place_detail`
* `places:place_list`
* `kwargs={'pk': self.object.pk}`

## 13-3. 템플릿에서 `places` 가 안 보이는 경우

`ListView` 에서는 기본 템플릿 변수명이 `object_list` 일 수 있습니다.
기존 템플릿에서 `places` 를 쓰고 있다면,
반드시 아래처럼 지정해야 합니다.

```python title="places/views.py"
context_object_name = 'places'
```

## 13-4. 수정/삭제 권한 체크가 안 되는 경우

`AuthorRequiredMixin` 순서와 `test_func()` 를 확인합니다.

보통 아래처럼 두는 것이 자연스럽습니다.

```python title="places/views.py"
class PlaceUpdateView(LoginRequiredMixin, AuthorRequiredMixin, UpdateView):
    ...
```

## 13-5. 페이지 버튼이 안 보이는 경우

데이터 수가 `paginate_by` 보다 적으면,
`is_paginated` 가 `False` 이므로 버튼이 보이지 않습니다.

즉 오류가 아니라 정상일 수 있습니다.

테스트할 때는 장소를 7개 이상 만들어보세요.

# 14. 이번 편에서 특히 기억해야 할 핵심 정리

이번 편의 핵심은 단순히 “함수형 대신 클래스형”이 아닙니다.

정확히는 아래를 익히는 것입니다.

## 14-1. CRUD는 제네릭 뷰로 정리할 수 있다

반복되는 목록/상세/생성/수정/삭제 패턴은
Django가 이미 아주 잘 준비해둔 구조가 있습니다.

## 14-2. 저장 직전 추가 값은 `form_valid()` 에서 넣는다

작성자(author) 같은 값은
폼 입력값이 아니라 서버에서 보정해야 하므로,
`form_valid()` 가 핵심 포인트입니다.

## 14-3. 권한 검사는 믹스인으로 재사용 가능하다

작성자 본인만 수정/삭제 가능하게 하는 정책을
공통 믹스인으로 묶으면 코드가 훨씬 깔끔해집니다.

## 14-4. 목록은 페이지네이션이 들어가야 아카이브다

아카이브 서비스는 데이터가 계속 쌓이므로,
페이지네이션은 옵션이 아니라 거의 필수에 가깝습니다.

```python title="places/views.py"
def signup(request):
    if request.user.is_authenticated:
        return redirect('places:home')

    if request.method == 'POST':
        form = SignUpForm(request.POST)
        if form.is_valid():
            user = form.save()
            login(request, user)
            messages.success(request, '회원가입이 완료되었습니다. 바로 로그인되었습니다.')
            return redirect('places:home')
    else:
        form = SignUpForm()

    return render(request, 'registration/signup.html', {'form': form})
```

# 17. 마무리

이번 3편에서는 새로운 기능을 크게 추가하지 않았습니다.
대신 이미 잘 동작하던 프로젝트를,
**더 깔끔하고 재사용 가능하고 확장하기 좋은 구조**로 정리했습니다.

이 과정이 중요한 이유는,
프로젝트가 커질수록 “새 기능 추가”보다 “기존 구조를 잘 정리하는 능력”이 더 중요해지기 때문입니다.

특히 이번 편에서 반드시 기억해야 할 것은 아래입니다.

* CRUD는 제네릭 뷰로 정리할 수 있다.
* `form_valid()` 는 저장 직전 값을 보정하는 핵심 포인트다.
* 권한 검사는 믹스인으로 재사용할 수 있다.
* 목록 페이지는 페이지네이션이 들어가야 아카이브답다.

이제 다음 4편에서는,
이렇게 정리된 구조를 바탕으로 **Django REST Framework(DRF)** 를 붙여서
추억 장소 데이터를 API로도 다룰 수 있게 확장해보겠습니다.

즉 다음 편부터는,
브라우저 템플릿 기반 서비스에서 한 단계 더 나아가
**웹 + API를 함께 다루는 구조**로 진입하게 됩니다.
